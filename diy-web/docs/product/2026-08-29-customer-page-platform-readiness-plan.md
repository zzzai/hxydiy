# 荷小悦顾客端：页面完善与跨平台准备计划

**状态：** 待实施

## 一、结论

当前顾客端适合继续作为 H5 生产版本，但不能把现有 React/Vite 页面直接当成微信小程序或原生 App 页面使用。

可以复用的部分包括：

- `domain`、选单计算、价格身份、服务位绑定和状态边界。
- API 合同、会员/匿名身份模型、评价和埋点数据结构。
- 现有测试用例、验收标准、菜单数据和产品文案。

需要适配或重写的部分包括：

- 依赖 `window/document/history` 的页面导航、弹层历史和边缘滑动返回。
- `localStorage`、浏览器在线状态、定时器和确认对话框。
- CSS 布局、滚动容器、图片加载行为和 `framer-motion` 动画。
- `lucide-react` 图标和部分浏览器专属无障碍实现。

## 二、推荐技术路线

### 微信小程序

推荐后续采用 Taro/React 兼容路线：保留业务核心和 API 层，页面组件按小程序运行模型重写。预计业务逻辑和测试可大量复用，页面表现层需要重新适配。

不建议把 H5 直接放进小程序 WebView 作为最终方案：上线快，但分享、返回、授权、支付和离线体验受限，且无法充分利用小程序原生能力。

### App

- 短期验证：可用 WebView 包装现有 H5，最快复用当前页面，但体验与系统能力有限。
- 长期产品：采用 React Native 或 Flutter 重写界面，复用 API、业务规则、价格模型和测试数据。

## 三、现在就应遵循的页面原则

- 业务计算、价格格式化、推荐（未来再做）、选单状态和服务状态不直接依赖浏览器对象。
- 页面导航、存储、网络状态、系统返回、震动和弹窗通过可替换适配层提供。
- 组件优先使用语义化按钮、列表、表单和状态组件，避免依赖 DOM 查询作为业务依据。
- 所有页面状态都能用显式数据表示：加载、空状态、编辑中、已提交、服务中、已完成、只读和错误。
- 价格展示只接受统一的价格模型，不在 JSX/CSS 中临时拼接身份逻辑。
- 现有瑞幸式 H5 视觉保持不变；未来小程序/App 只做平台原生布局适配，不改变业务含义。

## 四、现有页面完善顺序

### 第 1 阶段：入店与服务位

- 二维码进入、门店入口、服务位选择和服务位状态提示统一。
- 明确“当前服务位”“可选服务位”“已占用/需前台处理”三类状态。
- 刷新、返回和重新扫码不串位。

### 第 2 阶段：项目菜单

- 保持左侧分类、右侧项目列表和单字圆圈导航。
- 项目卡只承担浏览和进入详情；价格、时长、计费方式一眼可读。
- 空数据、加载失败和网络恢复状态完整呈现。

### 第 3 阶段：项目详情

- 顶部主图、简介、基础价格、服务流程、偏好和加购区层级统一。
- 详情顶部只显示当前项目价格，底部显示当前项目配置价格。
- 会员、非会员、匿名状态视觉明确；会员不出现领券或会员卡推荐。
- 所有选择项支持触控、键盘和只读状态。

### 第 4 阶段：底部选购与清单

- 待提交草稿、已提交服务和历史记录分区展示。
- 数量、门店价、会员价、节省金额和预计合计不重叠。
- 提交成功后草稿清空；返回菜单和刷新后边界保持一致。

### 第 5 阶段：服务状态、到店记录与评价

- 顾客可看到等待服务、服务中、服务完成和待评价状态。
- 评价只在服务完成后出现；已评价状态明确。
- 网络失败、接口超时和服务位释放都有恢复路径。

### 第 6 阶段：跨平台适配层

- 抽离存储、导航、网络状态、系统返回、弹窗和定时器适配接口。
- 保持业务核心在浏览器、小程序和 App 中使用同一套测试。
- H5 继续生产运行，小程序/App 作为独立表现层逐页迁移。

## 五、验收门槛

- H5 现有顾客流程不回退：扫码、选购、提交、状态、评价全部可用。
- 页面优化不引入轻推荐功能。
- 业务核心测试与平台适配测试分离。
- 小程序/App 迁移时不复制一份价格或选单逻辑。
- 任何平台都不能覆盖二维码服务位、会员价格或已提交清单的边界规则。
