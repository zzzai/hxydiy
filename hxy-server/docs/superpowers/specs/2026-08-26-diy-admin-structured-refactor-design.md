# 荷小悦 DIY 管理后台结构化重构设计

日期：2026-08-26

## 1. 目标与边界

在不改写 DIY 业务事实、数据库和服务端状态机的前提下，将现有 React/Vite + Ant Design 管理后台整理为清晰的资源化结构，吸收 Refine 的 data provider、资源、权限和页面分层思想。当前不做 Refine 全量重写，也不引入预约、前台、财务或技师派单流程。

生产唯一入口仍为 `https://diy.hexiaoyue.com/admin/`。新版本完成本地和服务器验证后一次性切换；生产期间不并行暴露新旧后台。

业务范围：

- 经营：今日运营、服务位看板、DIY 选单、加选确认、服务结束、线下结算、异常处理、评价和审计。
- 资源：门店、房间容器、沙发、床位、二维码。
- 内容：项目、可选项、商品、价格和页面内容。
- 顾客：用户、会员、标签、分群、顾客画像记录。
- 营销与分析：优惠券、自动化规则、经营分析。

## 2. 角色与门店隔离

第一版只展示当前门店，不显示切店器，但所有请求和资源继续带服务端确认的 `store_id`，为未来多店切换保留边界。

- `manager`（管理员/店长）：当前门店全部后台权限，包括服务位操作、选单确认、结算、内容价格、会员、营销、员工、审计和门店配置。
- `technician`（技师）：可登录并查看本店全部服务单（默认进行中，支持历史筛选），可新增本次服务记录和顾客画像标签/文字记录；不能改价、确认选单、结算、释放服务位、管理配置或查看其他门店。

现有 `admin/staff` 兼容期仅作为后端迁移映射：`admin -> manager`、`staff -> technician`。UI 不再使用 `staff` 作为“前台”含义；不新增前台、财务或派单角色。权限必须由后端校验，前端菜单隐藏只用于体验。

## 3. 前端架构

保留 React/Vite、Ant Design、HashRouter 和现有 API 路径。新增以下结构边界：

- `src/core/auth`：登录、当前员工、角色权限、门店上下文和 401 处理。
- `src/core/dataProvider`：统一 GET/POST/PATCH/DELETE、错误归一化、幂等键和请求缓存；页面不再直接拼接重复 axios 逻辑。
- `src/core/resources`：按资源声明列表、详情、创建、编辑、删除和自定义动作。
- `src/layouts`：统一侧栏、当前门店、角色菜单、响应式布局和全局反馈。
- `src/features/operations`：服务位看板、选单、服务动作、结算、异常和审计时间线。
- `src/features/catalog`：项目、可选项、商品、价格、发布和页面内容。
- `src/features/customers`：用户、会员、标签、分群和画像记录。
- `src/features/resources`：房间/床位/沙发/二维码；不包含技师派单。

Refine 可在后续标准 CRUD 页面中局部引入，但本轮不强制新增依赖；核心服务流程使用现有自定义页面和 Ant Design 组件，以保持状态机语义清晰。

## 4. 信息架构与页面

菜单只保留 DIY 业务需要的页面：

- 今日运营：待确认选单、待服务、服务中、待结算、待离位、异常提醒。
- 服务位看板：8 个大厅沙发、9 个房间床位；房间容器只做分组展示，不作为可占用服务位。
- 服务单：选单当前版本、历史版本、加选请求、实际服务项、价格快照、服务状态。
- 结算与异常：线下收款、减免、退款登记、强制释放、原因和审计。
- 顾客画像：用户基础信息、标签、技师新增记录、历史更正链；禁止医疗诊断和疗效承诺用语。
- 项目与价格：12 个正式项目、可选项、会员/门店/团购价、发布校验和版本记录。
- 资源与二维码：门店空间、房间、床位、沙发和二维码状态。
- 会员与顾客：会员状态、标签、分群；所有数据按当前门店过滤。
- 营销与内容：优惠券、自动化规则、页面内容、分析、审计。

明确移除预约列表、预约状态、技师分配/换技师、提成和前台专属文案。历史 API 可以暂时保留兼容，但不得被新 UI 调用。

## 5. 核心数据流

页面通过 `dataProvider` 访问现有 `/api/v1/admin` 和 `/api/v1/admin/v2` 接口。服务位动作仍调用服务端状态机：普通操作只显示“确认服务”和“服务结束”；服务完成不等于离位，清洁和物理资源释放仍遵循现有 DIY 契约。提交、确认、加选、结算、释放、画像记录和更正均展示操作者、时间、门店和前后状态。

技师查看服务单时默认读取当前门店全部服务单，列表按进行中优先；画像写入使用新增记录，不覆盖历史。管理员可查看完整历史和更正链。

## 6. 迁移策略

1. 先在现有工作区完成结构化重构和测试，不回滚或覆盖当前 `hxy-server` 未提交改动。
2. 先迁移登录、布局、权限和今日运营/服务位，再迁移服务单、结算、画像，最后迁移内容、顾客、营销和审计页面。
3. 每个阶段保持现有 API 契约；若发现 API 与业务边界不一致，先补后端测试和兼容适配，再调整页面。
4. 生产切换前生成前端构建 Manifest，核对后端、管理端和顾客端版本一致性；完成数据库备份、服务器构建、健康检查和关键只读/写入流程验证后，原子切换 `current`。

## 7. 测试与验收

- 管理端：角色菜单、技师只读/画像写入、服务位状态动作、选单确认/加选、结算/异常、项目发布、顾客门店隔离和响应式页面测试。
- 后端：管理员/技师权限、所有管理 API 的 `store_id` 隔离、画像记录和更正、状态机、价格快照、审计和异常释放测试。
- 构建：管理端生产构建必须成功；不得出现预约入口或派单入口。
- 服务器：在生产备份恢复库完成相关迁移/回滚演练；发布前执行 Manifest 校验和公网健康检查。
- 现场验收：扫码选位、提交选单、店长确认、服务结束、结算/离位/清洁，以及技师登录查看服务单并记录画像。

## 8. 非目标

本轮不建设在线支付、预约时间槽、自动排钟、技师分配、提成、跨店借调、AI 自动决策，也不把小程序后台纳入本次重构。

## 9. 多维度审核结论（2026-08-26）

本规格在实施前需要完成以下修订；未完成 P0 项不得进入生产切换。

### P0 阻断项

1. **角色迁移不可直接替换字符串。** 当前 `Staff.role` 仍为 `admin/staff`，技师档案在独立 `technicians` 表，且 `Staff.technician_id` 可为空。必须先盘点账号，明确 `manager` 与 `technician` 的迁移映射；技师账号必须绑定唯一 `technician_id`，无法绑定的账号不得自动获得技师权限。历史审计保留原角色值并在展示层翻译。
2. **门店隔离必须补齐。** 当前静态检查显示行为分析部分查询未带 `EventLog.store_id`，热门项目通过全局 `Project.id` 读取；`CouponTemplate` 当前模型没有 `store_id`，券列表/新增/更新也没有门店条件。所有顾客、会员、标签、订单、服务、事件、券、配置和审计查询必须按当前员工门店过滤，并增加跨店拒绝测试。
3. **物理运营边界必须落到 UI 和 API。** 智慧宝负责真实开沙发、开房间、派钟、离位、清洁和物理资源释放；DIY 后台不应展示或调用技师分配、确认离位、完成清洁、普通物理释放等动作。DIY 只保留电子菜单、服务确认、服务结束、评价、画像和审计；结算归属若保留在 DIY，必须单独写清与智慧宝的账单事实边界。
4. **移除业务残留。** 新 UI、路由、菜单和默认跳转必须删除预约页面、`today-appointments` 入口、预约文案、技师分配/房间绑定操作和派单入口。后端旧接口可暂时兼容，但新管理端不得调用。

### P1 必须补齐

1. **技师权限矩阵。** 明确每一个 endpoint 的 `manager`/`technician` 访问结果。技师只能查看本店服务单并新增自己的服务记录；画像接口必须自动使用当前技师身份，禁止提交任意 `technician_id`，经理代录须显式审计。
2. **画像数据最小化与字段治理。** `profile` 当前是任意 JSON，需定义允许字段、长度、可见角色和脱敏规则；“结节”等可能涉及健康信息的内容应改为非诊断性的服务提示，并限制导出和日志回显。继续保留医疗诊断词拦截和新增记录/更正链。
3. **技师服务单可见范围与字段。** “查看全部”解释为本店全部服务单；默认进行中、历史可筛选。手机号、会员状态、画像和价格字段需按权限脱敏，分页上限和排序写入接口契约。
4. **dataProvider 落地方案。** 明确是否引入 TanStack Query 或局部 Refine，统一缓存键、失效策略、幂等键、并发版本冲突、401/403/409 错误和操作反馈，避免只改目录而不改变重复请求逻辑。
5. **多店演进边界。** 当前门店管理员只能管理绑定门店；总部/平台管理员不属于当前业务角色。`/stores` 主数据页面暂不向门店管理员开放，未来增加平台角色时另行设计权限和审计。

### P2 质量项

- 删除或隔离旧预约组件、派单组件和无业务用途的图标/文案，避免误导员工。
- 为菜单无预约、无派单、角色菜单和响应式布局增加前端回归测试。
- 将生产切换、数据库备份、Manifest 校验、健康检查和现场验收作为发布门禁，而不是仅作为文档说明。
