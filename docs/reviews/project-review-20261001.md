# 荷小悦 DIY 项目整体评审与下一阶段开发规划

评审日期：2026-10-01。性质：只读技术与业务闭环评审；开发计划尚未派发。本报告不代表修改、合并或生产发布。

## 1. 结论

项目已经有真实生产系统的基础，并非需要重做的演示项目：三端、服务位短码、共享草稿、服务交接、到店反馈、会员来源卡、权限与发布门禁均有实现和测试。

但目前不能认定为“已全面完成、可无人兜底地扩大使用”。本次复现两个高优先级缺陷：来源卡会员在后台确认时可能从会员价变回门店价；生产环境未配置小程序密钥时，旧登录接口仍可签发调试身份令牌。另有储值权益更新缺口、磁盘容量风险及现场验收缺口。

下一阶段的目标不是增加模块或换框架，而是完成：**扫码进入菜单 → 共同选购 → 正确核验会员并报价 → 前台确认 → 技师执行 → 评价/记录 → 服务位释放**，形成价格、身份、权限与状态一致的可恢复业务闭环。

## 3. 已确认的问题

### R01 · P1 · 来源卡会员确认价格与预览不一致

**要求**：年度权益卡、余额大于零的在用储值卡均应按本店有效权益计价；已核验会员身份后，确认时重新检查权益并冻结正确价格。

**实际**：`hxy-server/app/api/selections.py:133` 的预览使用 `has_membership`；但 `:159` 的确认价格上下文仍使用 `user.is_member/member_type/member_expire_at` 旧汇总。`hxy-server/app/api/admin_v2.py:1238` 的确认入口传入确认时间，进入此分支。

**复现**：仅持有效来源储值卡、旧会员标记为 false 的顾客，预览 2990 分；后台确认 HTTP 200 后，冻结金额 3990 分。复现器：`tools/audit/review_20261001.py`。这是数据模型迁移后两套权益判定分叉，不是前端金额显示问题。尚未查询生产历史订单，不断言已发生真实顾客损失。

**修复方向**：确认、追加、修订与预览统一调用本店、指定时刻的有效权益判定。保留员工动态码核验边界及价格快照不可追溯重写规则，不靠批量修改旧会员标记掩盖问题。

**验收**：来源年度卡 / 储值卡 / 多卡并存 / 到期和耗尽 / 扫码后失效 / 异店拒绝 / 未核验身份等矩阵；真实 HTTP 走报价到确认及受控修订；有效会员金额一致，失效时明确返回或重新报价，历史确认金额不被改写。

### R02 · P1 · 旧登录接口的开发回退没有生产隔离

**要求**：生产客户令牌必须来自验证过的身份链路。

**实际**：`hxy-server/app/api/auth.py:349` 的 `/auth/login` 在未配置 `wx_appsecret` 时直接用传入 code 生成 `dev_` 身份，没有判断环境。本次只读核验确认生产正好未配置该密钥。

**复现**：隔离测试设置为 production、清空小程序密钥，任意测试 code 返回 HTTP 200 并签发客户 token。未向生产调用此写接口。

**影响边界**：不可信调用者可经旧入口获得应用客户身份；不能据此声称可冒用已验证手机号会员、获得管理员权限或读取所有顾客资料。

**修复方向与验收**：生产未配置时 fail closed；开发模拟必须显式限定开发/测试环境。缺密钥、非法微信 code 均不得签发生产令牌；现有 H5 短信登录不受破坏。审查是否存在历史 `dev_` 身份需另做脱敏只读统计，不自动删用户。

### R03 · P1 业务闭环缺口 · 来源储值余额没有持续更新路径

**要求**：储值卡金消耗完即失去会员权益。

**实际**：`docs/contracts/member-card-entitlements.md:35` 声明 `balance_realtime=false`；`:37` 和 `docs/operations/member-card-import.md` 明确当前导入器拒绝变化快照，后台权益说明只读，人工更新方案尚未确定。已导入的正余额不会因为外部系统发生消费而自行变成零。

**风险**：即使修复 R01，只要本地余额未更新，外部已耗尽的卡仍可能被判定有效。定时重复运行导入器不能解决此问题。

**建议**：外部接口仍按要求暂缓。先提供有审计的来源卡状态/余额更新命令或后台入口，记录核对人、依据、更新时间、前后值，支持预览与幂等。只维护外部权益事实，不建设 DIY 充值、扣款或赠金钱包；继续遵守用户要求，不向顾客展示来源余额。

**待确定的运营决策**：由哪位店长负责核对，日终批量还是消费后更新。在确定之前不能承诺“外部耗尽后自动立即失效”，也不能擅自让所有已导入会员失效。

### R04 · P1 运维风险 · 生产根盘使用率 90%

**证据**：本次 `hxy` 只读磁盘检查；当前服务仍正常，不是已发生磁盘故障。

**影响**：发布包、镜像、日志、数据库备份和恢复演练需要额外空间；继续发布可能失败，也可能挤占数据库写入空间。

**建议**：发布前容量检查与门禁；仅识别并保全后处理本项目过期发布物及日志，明确保留数与回滚目标；核实异机备份与恢复记录。仓库部署脚本已有发布前备份、恢复演练和应用回滚，但本次没有验证异机备份或日常告警是否有效，不能声称已具备灾备。

**验收**：确认可用空间足够覆盖下一次构建、备份与演练的峰值及余量；建议预警 80%、严重 90%，阈值结合实际峰值确定。恢复演练成功，保护同机其他服务及最新回滚包。清理/扩容按具体目标确认，不执行全局 prune。

### R05 · P2 · 顾客共享草稿轮询缺少弱网保护

**证据**：`diy-web/src/App.tsx:1190` 每 3 秒轮询，只有保存/提交保护，没有请求在途去重；可见性事件只触发刷新，没有在隐藏时停用该轮询。`diy-web/src/api.ts:191` 通用请求没有默认超时。菜单版本同步另有可见性处理，不能以它代替共享草稿检查。

**风险**：慢响应时多个读取重叠，隐藏页面继续请求；没有做本次负载实测，不将其描述为已发生生产故障。

**验收**：模拟响应超过 3 秒、离线、页面隐藏、返回前台、令牌过期和组件卸载；同一选单最多一个在途轮询，有超时/取消、失败退避、恢复后立即同步；保持服务端版本冲突保护及提交后只读。

### R06 · P2 · 测试和类型覆盖没有覆盖最关键的跨环节交接

**证据**：相关既有后端测试通过，而 R01/R02 仍可复现。`hxy-server/tests/test_admin_catalog_schemathesis.py:87` 当前 Schemathesis 范围是项目、商品两个 GET 列表。顾客端 `src/api.ts` 仍有手工接口类型。部分前端测试（如 `admin-react/tests/membership-closure.test.ts`）主要断言源码字符串，不能证明真实操作成功。

**建议**：保留这些现有保护，不把 Schemathesis 通过等同于业务闭环通过。优先新增身份→权益→报价→确认、共享草稿→冲突→提交→只读的真实行为验收；再逐步给高风险顾客接口接入 OpenAPI 类型。测试造数据与接口模糊测试只能在隔离环境执行。

## 5. 分阶段开发计划

### 阶段 A：先封住真实用户风险

目标：消除 R01/R02，并具备下一次安全发布的容量。优先级最高，完成前不扩大门店使用规模。

| 编号 | 主执行窗口 | 修改边界 | 验收和依赖 |
|---|---|---|---|
| SAFE-01 | 管理后台＋后端 | 旧登录生产回退及对应测试/安全契约 | 生产缺配置不发 token；H5 登录不回归；单独小 PR |
| PRICE-01 | 管理后台＋后端 | 统一权益确认计价及确认/修订测试、会员契约 | R01 矩阵通过；单独小 PR，不追溯改历史金额 |
| OPS-01 | 总控协调运维执行 | 项目容量盘点、门禁、保留策略、恢复证据 | 先只读识别，具体清理范围另确认；不触碰其他系统 |

SAFE-01 与 PRICE-01 由同一后端写入者顺序推进，避免两人同时修改 auth、selection、membership 或生成 OpenAPI。总控只收最终报告与协调发布，不重复实现和全套验证。

### 阶段 B：补齐单店运营闭环

目标：顾客、店长、技师共同完成一次真实服务，并可从弱网和重复操作恢复。

| 编号 | 主执行窗口 | 修改边界 | 验收和依赖 |
|---|---|---|---|
| MEMBER-02 | 管理后台＋后端 | 来源卡受控更新、状态审计、店长权限；不做钱包 | 运营责任/频率确定后实施；正数→零、停卡、重复导入、异店拒绝，金额不外露 |
| CUSTOMER-02 | 顾客端 | 共享草稿轮询/恢复、交互错误提示和定向测试 | R05 矩阵，双设备共享只到提交前；不改后端权限和价格 |
| TECH-02 | 技师端 | 服务生命周期和记录交互的专项验收及发现的端内缺陷 | 真机失败保留、重试幂等、本人更正、他人信息保护；涉及 API 缺口交给后端唯一写入者 |
| FIELD-01 | 总控组织，门店参与 | 验收矩阵与证据，不另造业务实现 | 阶段 A 已发布、三个执行窗口各自回执可定位，按第 6 节验收 |

顾客端和技师端在不碰共享文件的前提下，可与阶段 A 的后端修复并行。不得用“没有新功能”误判技师端已验收，也不为凑任务重做已完成模块。

### 阶段 C：单店稳定后完善连锁管理

1. 继续已立项 `BRAND-CATALOG-004`：总部模板、门店覆盖价、继承/覆盖优先级、发布及审计；先 API/合同，再管理界面。不得改写已确认订单价格。
2. 将会员、选单及服务位高风险接口纳入生成类型与行为验证，避免一次性全项目重构。
3. 统一详情图尺寸、背景、品牌人物、信息层级和图片体积；先清单审查，合格图保留，不合格图按批替换并验收移动端。
4. 外部会员系统接入继续独立排队；恢复后先验证门店归属、字段含义与同步权限，再做增量同步、对账、失败恢复。不把外部 Token 作为阶段 A/B 的前置条件。

排期按关卡而非预设“几天全部完成”：阶段 A 优先连贯完成，阶段 B 可按端并行，阶段 C 在单店验收过后开展。每项只有一个执行窗口，派发仅含目标、实际工作区、修改边界、验收条件和证据位置。

## 6. 面向真实用户的放行标准

- 价格：年度、储值、非会员各完成一次核验→选购→前台确认→技师接单核对；金额一致且确认后冻结。
- 身份与权限：真实短信登录、退出/失效；匿名不见他人信息，技师不读私人评价原文，跨店访问拒绝。
- 扫码：8 个沙发逐个核对码与位置；双设备同位可协作；切位不覆盖原位；提交后其他人只能浏览；停码/换码拒绝旧入口。
- 服务：开始、结束、异常恢复、记录重试与释放位后再扫码跑通。历史记录和确认订单不被新会话覆盖。
- 弱网：重复点击只提交一次；断网不丢未提交输入；恢复后不静默覆盖他人选单。
- 运营：来源储值更新有负责人和审计，年度按真实到期日判定，不能把导入快照称为实时余额。
- 运维：发布对应精确提交，容量与备份检查通过；回滚方案可执行。健康接口正常只证明服务响应，不代替以上业务验收。

每条记录设备、时间、服务位、脱敏账号类型、结果与问题编号；不在共享报告写完整手机号、二维码 bearer 链接或凭据。

## 7. 调用与协作成本控制

- 保留原有三端窗口和一个总控；一个任务只由一个执行窗口完成。
- API/OpenAPI/价格/会员/迁移文件由后台＋后端窗口单一写入；顾客和技师只改各自端内范围。
- 复用本报告及缺陷复现证据，不让三端各自重新扫全仓。
- 固定验收交给脚本；脚本输出精简结果与报告路径，失败时才读取相关日志。CI/发布只等待最终状态，不唤醒模型轮询。
- 不取消已有发布/权限/数据保护门禁；不在此阶段引入 Jev、新编排平台或替换前端框架。
