# 连锁品牌账号授权与项目价格分层设计

## 1. 基本信息

- Feature ID：`BRAND-ACCESS-003`、`BRAND-CATALOG-004`
- 当前状态：`Spec Ready`
- 总控负责人：总控窗口
- 执行窗口：管理后台
- 依赖：`BRAND-CATALOG-004` 依赖 `BRAND-ACCESS-003` 的作用域令牌和授权校验
- 相关长期契约：`docs/product/hxy-diy-admin-platform-prd.md`、`docs/contracts/admin-catalog-openapi-v1.md`

## 2. 背景与已确认事实

生产账号 `admin` 登录后的对外角色为 `manager`，并绑定 1 号店。现有系统将“绑定门店的历史 `admin`”兼容为店长；店长只能上下架本店目录，不能编辑项目主数据和价格。前端按该规则隐藏编辑入口，后端也用总部管理员校验阻止店长改价，因此本问题不能通过单独显示按钮解决。

业务方已确认：

- 一个账号可同时拥有多角色、多门店授权。
- 项目采用“总部统一模板 + 门店价格覆盖”模型。
- 首期角色为品牌管理员、总部运营、店长和门店员工；技师继续使用技师端。
- 现有 `admin` 账号升级为首个品牌管理员，保留密码，解除固定门店绑定并撤销旧会话。

## 3. 目标与非目标

### 3.1 目标

- 让账号、角色与管理范围分离，支持一人管理多店或同时承担总部与门店职责。
- 登录后显式选择总部或具体门店工作台，所有请求都绑定当前作用域。
- 由总部统一管理项目主数据、标准价和门店覆盖规则，门店只在授权边界内调整本店价格和上下架。
- 保留现有门店项目 ID、历史订单、选单和版本化目录引用，迁移不改变公开价格。

### 3.2 非目标

- 首期不建立独立区域经理角色；多店授权已能覆盖该场景。
- 不引入单点登录、企业微信或外部身份提供方。
- 不改变顾客端下单、支付、库存、采购或履约范围。
- 不用前端菜单或按钮隐藏代替后端授权校验。

## 4. 账号、角色与作用域

### 4.1 数据模型

`staff` 继续作为登录主体，保留凭证版本、状态和技师兼容字段。新增角色授权表，至少包含：

- `staff_id`
- `role`：`brand_admin | hq_operator | store_manager | store_staff`
- `scope_type`：`brand | store`
- `scope_id`：品牌范围为空，门店范围为门店 ID
- `status`：`active | disabled`
- 创建人、创建时间、更新时间

同一账号可有多条有效授权。数据库必须防止重复的“账号 + 角色 + 作用域”授权，并校验品牌角色不得绑定门店、门店角色必须绑定有效门店。

### 4.2 登录和工作台切换

1. 用户使用现有管理后台登录入口。
2. 凭证验证通过后，服务端返回账号摘要和可选工作台，不直接信任前端提交的角色或门店。
3. 只有一个工作台时自动进入；多个工作台时进入选择页。
4. 选择或切换工作台时，服务端核对实时授权并签发短期作用域令牌。
5. 页面顶部始终显示当前角色和范围，例如“品牌管理员｜总部”或“店长｜紫薇壹号店”。

作用域令牌必须绑定账号 ID、授权 ID、角色、作用域和凭证版本。授权撤销、账号停用、密码修改或角色变更后，相关令牌不得继续生效。

### 4.3 权限矩阵

| 能力 | 品牌管理员 | 总部运营 | 店长 | 门店员工 |
|---|---:|---:|---:|---:|
| 管理品牌管理员 | 是 | 否 | 否 | 否 |
| 分配非品牌管理员角色 | 是 | 是 | 否 | 否 |
| 维护总部项目模板 | 是 | 是 | 否 | 否 |
| 设置标准价和覆盖规则 | 是 | 是 | 否 | 否 |
| 修改允许覆盖的本店价格 | 是 | 是 | 是 | 否 |
| 本店上下架 | 是 | 是 | 是 | 否 |
| 门店日常运营 | 切换到授权门店后 | 切换到授权门店后 | 是 | 按现有只读范围 |

总部角色必须具有相应门店授权后才能进入具体门店工作台，不将品牌管理权自动视为任意门店的日常运营身份。

## 5. 总部项目模板与门店实例

### 5.1 总部项目模板

新增总部项目模板，统一管理：项目编码、名称、分类、时长、简介、主图、详情、标签、展示顺序和品牌启停状态。

现有 `Project` 继续作为门店可销售实例，新增对总部模板的关联。历史订单、选单、加项和版本化选项继续引用原门店项目 ID，不做引用重写。

### 5.2 价格政策

门店价、会员价和团购价分别设置：

- 总部标准价；
- 是否允许门店覆盖；
- 可选最低价和最高价；
- 是否强制门店使用总部价。

有效价格解析规则：

1. 强制总部价时，总部标准价生效。
2. 允许覆盖且本店存在合法覆盖值时，本店覆盖价生效。
3. 其余情况使用总部标准价。

店长提交的覆盖价必须在允许范围内；规则被锁定或项目被品牌停用时，服务端必须拒绝写入。

### 5.3 上下架

- 总部停用项目后，所有门店不得再上架。
- 店长只能修改授权门店实例的上下架状态。
- 项目名称、时长、详情等品牌主数据只能由总部修改。

## 6. 管理后台交互

- 新增工作台选择页；单授权账号可自动跳过。
- 顶部新增工作台切换器，展示当前角色与范围。
- 新增“账号与授权”页，支持一个账号分配多条角色/门店授权。
- 总部项目页维护模板、标准价、覆盖规则和门店分发情况。
- 门店项目页同时显示总部标准价、本店有效价、覆盖来源和可编辑范围。
- 没有编辑权时明确显示权限说明，不只是隐藏按钮。

## 7. API 与失败语义

实施计划阶段将具体路径写入版本化 contract 和 OpenAPI。本设计冻结以下语义：

- 登录返回账号摘要和可选工作台，不把一条历史 `role/store_id` 快照作为最终授权。
- 工作台切换必须由服务端验证授权并签发新令牌。
- 品牌主数据、价格政策、门店覆盖价和门店上下架使用不同写入契约。
- 跨作用域访问、授权被撤销、价格越界和品牌锁定必须返回稳定错误码与可读消息。
- 公开目录继续返回门店实际有效价格，不向顾客端暴露内部授权或定价规则。

## 8. 审计与安全边界

所有写操作至少记录：登录账号、当前授权、角色、作用域、目标门店、目标资源、变更前后值和发生时间。

密码、令牌和验证码不得进入 Git、文档、日志或审计详情。前端提交的门店 ID 不是授权证据；后端必须根据作用域令牌和实时授权重新校验。

## 9. 迁移和兼容

### 9.1 账号迁移

- 将现有 `admin` 账号迁移为 `brand_admin / brand` 授权。
- 保留密码哈希，移除旧的固定门店授权语义，递增凭证版本撤销旧会话。
- 其他历史账号按当前对外角色和门店范围生成等价授权，不扩大权限。

### 9.2 项目和价格迁移

- 以现有 14 个门店项目生成 14 个总部项目模板并建立关联。
- 保留门店项目 ID、历史引用和当前上下架状态。
- 将当前有效价复制为总部初始标准价和该门店初始有效价；迁移不主动调整价格。
- 迁移前后必须逐项比对公开目录的项目数量、项目 ID、状态和实际价格。

发布必须通过受保护迁移流程执行，先备份与恢复演练，再升级生产库。不通过浏览器、手工 SQL 或绕过门禁的临时命令修改生产账号。

## 12. 已考虑方案

### 采用：账号—角色—范围授权

此方案能支持多店、多职责、授权撤销和可审计的工作台切换，不依赖登录名推断身份。

### 不采用：继续扩展 `staff.role + store_id`

该方案改动小，但一个账号无法清晰表达多角色和多门店，会继续混淆身份、范围与登录名。

### 不采用：总部和门店分开建号

此方案实现简单，但同一人管理多店需要多个账号，不符合已确认的连锁经营模型。
