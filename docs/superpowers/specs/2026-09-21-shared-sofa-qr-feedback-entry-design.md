# 同一扫码入口的待评价提醒设计

- 日期：2026-09-21
- 范围：顾客端、服务位入口 API、评价 API
- 状态：已确认设计，待实施

## 目标

每个沙发继续只使用一个长期二维码。匿名顾客和登录顾客扫码后都直接进入现有选项目页；若当前身份存在已完成且未评价的服务，页面给出清晰但不阻断选购的待评价提醒。

## 非目标

- 不新增“选项目 / 去评价”中间页。
- 不允许仅凭沙发号评价，不开放公开评价入口。
- 不把浏览器 Cookie 推断为同一自然人、会员身份或跨设备身份。
- 不改变评价星级、标签、文字长度、幂等规则或服务结束资格。
- 不恢复旧选单，不复制旧项目，不改变当前沙发占用或智慧宝状态。

## 用户体验

扫码验证门店和沙发后仍进入现有项目列表。没有待评价时页面完全保持现状。

存在待评价时，在顶部主视觉下方展示轻量提醒卡：

```text
上次服务已完成，等您评价
花半分钟，说说这次体验
[去评价]
```

- 只有一条时，点击直接打开既有评价表单。
- 有多条时，先进入待评价列表；每条仅展示必要的完成时间、项目摘要和“去评价”。
- 提醒卡不遮挡项目列表，不自动弹窗，也不阻止加入服务或提交新选单。
- 提交成功后立即移除对应任务；没有剩余任务时提醒卡消失。
- 网络失败保留已填内容和待评价任务，可重试。

## 身份与权限

### 匿名顾客

服务端使用现有 `HttpOnly` 的 `hxy_browser_token` 找到当前浏览器对应的匿名顾客，只查询该匿名顾客在当前门店的已完成、未评价记录。浏览器标识仅作为当前浏览器访问边界，不升级为自然人身份。

匿名待评价列表不返回旧选单访问令牌。服务端为每条任务签发短期、单用途的评价凭证，至少绑定：

- 选单 ID；
- 匿名顾客 ID；
- 门店 ID；
- 用途 `service_feedback`；
- 过期时间。

提交时必须同时满足当前浏览器仍对应同一匿名顾客、凭证签名有效、门店和选单一致、服务已结束且尚未评价。评价成功或幂等命中后，该任务不可再次创建评价。

### 登录顾客

服务端使用当前有效 Bearer 令牌，只查询该账号本人的已完成、未评价记录。登录会话被替换后，旧令牌继续按现有规则失效。

当浏览器同时具有匿名 Cookie 和登录令牌时，提醒任务按两组来源合并并按选单 ID 去重：

- 当前登录账号本人记录；
- 当前浏览器尚未绑定到账号的匿名记录。

匿名记录不会自动改绑账号；只有既有明确登录绑定流程才能改变选单归属。前端按每条任务返回的提交方式使用 Bearer 或匿名短期评价凭证。

## 接口设计

新增只读接口：

```text
GET /api/v1/selection-sessions/pending-feedback?store_id={store_id}
```

请求可携带 Bearer 令牌，并自动携带同源 `HttpOnly` Cookie。响应只返回当前门店最多 20 条任务：

```json
{
  "items": [
    {
      "selection_session_id": "...",
      "service_completed_at": "...",
      "items": [{"name": "现煮草本泡", "quantity": 1}],
      "submit_mode": "customer" ,
      "anonymous_feedback_token": null
    }
  ],
  "total": 1
}
```

匿名任务的 `submit_mode` 为 `anonymous_browser`，并返回短期 `anonymous_feedback_token`；登录任务为 `customer`，不返回该凭证。响应不返回手机号、评价内容、原选单令牌、价格、技师信息或其他顾客信息。

既有评价接口扩展为可接受匿名短期评价凭证，例如请求头 `X-Feedback-Token`。鉴权优先级明确为：

1. 有效 `X-Selection-Token`；
2. 有效顾客 Bearer；
3. 有效 `X-Feedback-Token` 且当前浏览器身份匹配。

三种方式最终复用同一套服务结束、所有权、评分、标签、文字和幂等校验。

## 前端状态流

1. 服务位二维码校验和入口会话建立成功。
2. 项目、页面内容加载期间并行请求待评价任务；失败不阻断选项目页。
3. 有任务时显示提醒卡；一条直接打开表单，多条打开任务列表。
4. 评价表单复用现有 `FeedbackDialog`，仅切换提交凭证。
5. 成功后从本地任务列表移除；失败保持表单和输入。
6. 登录、退出登录、页面重新获得焦点时刷新任务，避免使用过期身份结果。

## 错误处理

- 无浏览器 Cookie 且无登录令牌：返回空列表，不创建匿名身份。
- Cookie 失效或历史错误绑定到手机号账号：不返回匿名任务，由既有入口流程完成身份自愈。
- 服务尚未结束、已评价、凭证过期或身份不匹配：提交被拒绝，不泄漏记录是否存在。
- 待评价读取失败：项目选择继续可用，只隐藏提醒并允许下次刷新重试。
- 重复点击或网络重放：返回既有评价结果，不新增第二条。

## 测试与验收

### 后端

- 匿名浏览器只得到自身、当前门店、已完成且未评价的任务。
- 登录顾客只得到本人任务；同时存在匿名任务时正确合并和去重。
- 无身份、跨店、其他浏览器、伪造/过期短期凭证均不能读取或提交。
- 未结束、已评价和重复提交继续遵守现有资格与幂等规则。
- 响应不包含旧选单令牌、手机号、技师或评价正文。

### 顾客端

- 无任务时首页不变化。
- 一条任务直接评价，多条任务进入列表。
- 提醒不阻断浏览项目、加入服务和提交选单。
- 匿名和登录提交使用正确凭证；成功后任务消失。
- 读取或提交失败时项目列表可用，表单内容不丢失。
- 页面聚焦、登录和退出登录后刷新任务。

### 发布边界

本地通过相关后端合同测试、顾客端交互测试、完整构建和 `git diff --check` 后才可合并。生产发布后分别验证匿名和登录顾客扫码、待评价提醒、评价提交与继续选购；自动化和公网 HTTP 200 不替代微信真机及门店现场验收。

## 实施交接（基于当前主干核对）

### 已有实现与必须复用的边界

- 服务位入口 `POST /api/v1/occupancies/entry-sessions` 已通过 `hxy_browser_token` 解析或创建匿名顾客，Cookie 为 `HttpOnly + SameSite=Lax`；待评价查询不得再次创建匿名身份。
- 浏览器实例始终指向匿名用户。当前手机号登录会在顾客持有有效选单凭证时，把该匿名用户的 `draft/submitted/confirmed` 选单、评价和到店记录迁移到手机号账号，但不会把浏览器实例改绑到账号。
- 因此待评价查询必须按数据库当前归属合并：有效 Bearer 对应账号的任务，加上当前 Cookie 仍对应匿名用户的任务，再按 `selection_session_id` 去重。已迁移到账号的选单只按 `customer` 返回，不能同时签发匿名评价凭证。
- 现有评价接口已经支持有效原选单凭证或本人 Bearer、服务结束资格检查，以及同一选单返回既有评价结果；`service_feedback.selection_session_id` 已有唯一约束。实现增量应复用这些规则，不另建第二套评价表或评价逻辑。
- 现有顾客端 `FeedbackDialog` 已做到未选星不可提交、失败不关闭表单、标签最多三项和文字最多 300 字；新入口只切换任务和提交凭证。

### 后端接口增量

#### 1. 待评价查询

`GET /api/v1/selection-sessions/pending-feedback?store_id={store_id}`

- Bearer 可选；同源 Cookie 自动携带。
- 没有 Bearer 且没有可解析的匿名浏览器 Cookie 时返回 `200 {"items": [], "total": 0}`，不得创建 `User` 或 `BrowserInstance`。
- Bearer 缺失时只查询 Cookie 对应匿名顾客；Bearer 有效时查询账号本人，并合并当前 Cookie 对应的尚未迁移匿名记录。
- Bearer 存在但无效、过期或已被其他设备替换时继续返回现有 `401`，不得静默降级为匿名结果。
- 只返回请求门店、存在权威 `actual_service_end_at`、尚无 `ServiceFeedback` 的记录，按完成时间倒序，最多 20 条。
- 项目摘要只保留 `name` 和 `quantity`；不返回价格、手机号、技师、评价正文、原选单访问令牌或健康信息。

建议响应模型固定为：

```json
{
  "items": [
    {
      "selection_session_id": "uuid",
      "service_completed_at": "2026-09-21T12:30:00Z",
      "items": [{"name": "现煮草本泡", "quantity": 1}],
      "submit_mode": "anonymous_browser",
      "anonymous_feedback_token": "short-lived-token"
    }
  ],
  "total": 1
}
```

`submit_mode` 只允许 `customer | anonymous_browser`。登录账号任务的 `anonymous_feedback_token` 必须为 `null`。

#### 2. 匿名短期评价凭证

建议复用当前服务端 JWT 密钥与算法，增加独立 `token_type=service_feedback`，有效期 15 分钟，不写入 URL、日志、埋点或本地持久化。至少包含：

- `selection_session_id`
- `customer_id`（必须是匿名用户）
- `browser_instance_id`
- `store_id`
- `purpose=service_feedback`
- `iat`、`exp`

提交时必须重新读取当前 `hxy_browser_token`，确认仍解析到同一 `browser_instance_id + customer_id`，并再次校验选单当前归属、门店、服务结束时间和未评价状态。仅验证 JWT 签名而不复核当前 Cookie 不合格。

该方案不需要新增数据库表或迁移。单用途由选单级唯一评价、提交时加锁和成功后的既有评价结果共同保证；过期后由查询接口重新签发，不续签旧凭证。

#### 3. 评价接口扩展

`POST /api/v1/selection-sessions/{id}/feedback`

新增可选请求头 `X-Feedback-Token`。鉴权优先级和失败规则固定为：

1. 请求携带 `X-Selection-Token` 时，只校验该凭证；无效即拒绝，不回退到其他身份。
2. 否则请求携带 Bearer 时，只校验当前登录账号本人；无效或已替换即返回现有 `401`。
3. 否则校验 `X-Feedback-Token` 与当前匿名 Cookie；任一不匹配统一返回不泄漏记录存在性的 `403`。
4. 三者都没有时返回 `401/403`，不得按沙发号、选单 ID 或来源参数放行。

鉴权完成后必须锁定 `SelectionSession`，在同一事务内检查服务结束、查询既有 `ServiceFeedback`、创建评价或返回既有结果，避免两个并发请求在“先查后写”窗口触发唯一约束错误。重复点击、网络重放和同凭证重试必须返回同一评价结果。

当前后端 `FeedbackIn` 仍允许最多 6 个标签和 1000 字，而已发布顾客契约与前端均为最多 3 项、300 字。共享后端窗口实现时必须把三种鉴权路径统一到同一份校验，并补合同测试；不得只对匿名凭证使用另一套限制。该差异应作为现有合同缺口显式处理，而不是借新入口改变顾客文案或评价规则。

### 顾客端任务

1. 在 `api.ts` 新增 `PendingFeedbackTask`、`getPendingFeedback(storeId, customerToken?)`，并把评价提交改成显式凭证联合类型：`selection | customer | anonymous_browser`；禁止根据字符串内容猜测令牌类型。
2. 入口会话成功后，与项目内容加载并行拉取待评价任务；读取失败只隐藏提醒并等待下次刷新，不改变 `boot`、项目列表、选单草稿或提交能力。
3. 待评价请求使用递增请求号，并绑定请求时的 `storeId + customerAuth.token`。响应返回后身份、门店或请求号变化则丢弃，避免登录、退出或切店后的旧响应覆盖当前任务。
4. 登录成功、退出登录、页面重新可见和窗口聚焦时刷新任务。退出登录后不得继续使用账号任务或 Bearer；匿名任务必须重新通过 Cookie 查询取得新短期凭证。
5. 一条任务点击提醒后直接把该任务设为 `activeFeedbackTask` 并打开现有 `FeedbackDialog`；多条先打开轻量任务列表。任务列表只展示完成时间、项目摘要和“去评价”。
6. `FeedbackDialog` 的 `submitted`、提交中状态和成功处理必须按当前任务维护，不能复用当前正在选购会话的 `serviceStatus`。后台刷新不得替换已打开表单的任务，确保提交失败时星级、标签和文字不丢失。
7. 成功后先按 `selection_session_id` 从本地任务列表移除，再后台刷新；没有剩余任务时提醒卡消失。刷新失败不恢复已成功任务，也不影响继续选购。
8. 首页提醒卡位于顶部主视觉下方，不自动弹出、不遮挡目录，不修改当前服务位、当前选单或“再次选购”逻辑。

### 后端窗口任务拆分

1. 把“只读解析现有匿名浏览器身份”提取为共享 helper；入口仍可创建身份，待评价查询只能读取现有身份。
2. 新增待评价响应 schema、查询路由与最多 20 条的所有权/门店/完成/未评价过滤。
3. 增加独立短期评价凭证签发和解析函数，禁止复用顾客登录令牌的 `token_type`。
4. 重构评价鉴权为三种显式凭证路径，并在选单行锁内完成资格检查和幂等创建。
5. 更新 OpenAPI、`docs/contracts/customer-account-profile.md` 与合同测试；如果后端实现改变跨端字段，必须与顾客端代码在同一发布切片中对齐。
6. 不改服务位二维码、占用状态机、选单归属迁移逻辑、价格、会员或智慧宝逻辑。

### 验收矩阵

| 场景 | 预期 |
| --- | --- |
| 无 Cookie、无 Bearer | 空列表，不创建身份 |
| 匿名浏览器 A / B | A 只能看到并评价 A 的当前门店任务，B 不可读不可写 |
| 匿名任务跨店查询 | 不返回；跨店令牌提交统一拒绝 |
| 登录账号本人 | 只返回当前账号本人未评价任务 |
| 同时有账号与匿名来源 | 合并后按选单 ID 去重；已迁移记录只走 `customer` |
| 登录令牌被替换 | 查询与提交均返回现有 `SESSION_REPLACED`，不降级匿名 |
| 匿名凭证伪造、过期、Cookie 轮换 | 统一拒绝且不泄漏记录存在性 |
| 服务未结束或已有评价 | 不出现在列表；直接提交按既有规则拒绝或幂等返回 |
| 两次并发提交 | 只生成一条评价，两次均得到同一结果，不出现 500 |
| 一条 / 多条任务 | 一条直达表单，多条先列表 |
| 待读取失败 | 项目浏览、加入服务、提交选单均正常 |
| 提交失败 | 表单内容和任务保留，可重试 |
| 提交成功 | 对应提醒立即消失，继续选购不受影响 |
| 登录、退出、聚焦期间旧响应返回 | 旧响应被请求号与身份快照丢弃 |

### 完成证据

- 后端：匿名/账号所有权、合并去重、跨店、令牌伪造/过期、Cookie 不匹配、服务资格、并发幂等和响应字段最小化的真实 HTTP 测试。
- 顾客端：API 请求头测试、身份切换旧响应测试、单条/多条交互、失败保留输入、成功移除任务、非阻断选购测试及生产构建。
- 发布后：分别用匿名微信浏览器和已登录顾客完成“同一码进入项目页 → 看到待评价 → 评价 → 继续选购”，另测无任务不出现提醒。自动化与公网 200 不替代真机和门店现场验收。
