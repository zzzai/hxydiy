# 技师账号生命周期管理设计

日期：2026-08-28  
状态：设计已获产品确认，待实施计划

## 目标

为荷小悦 DIY 的内部技师提供可控、可审计的账号生命周期：店长创建和管理账号，技师通过手机端使用账号和密码登录；停用或离职立即撤销登录能力，同时保留技师档案、服务记录、顾客服务参考和审计数据。

## 已确认决策

- 技师端不开放公众自主注册。
- 登录方式为“账号 + 密码”。
- 首次使用和忘记密码由店长生成一次性激活凭证，技师自行设置密码。
- 忘记密码不提供手机号自助找回，店长执行“重置登录”。
- `Staff` 是登录身份，`Technician` 是业务档案，二者通过 `Staff.technician_id` 关联，不合并为一个对象。
- “销户”在系统内表现为停用账号或办理离职，不物理删除任何业务历史。
- DIY 不接管智慧宝的开房、开沙发、派钟、离位、清洁和物理资源释放。

## 范围

### 本期包含

- 技师档案与登录身份的绑定校验。
- 店长在本店范围内开通登录、重置登录、停用账号、恢复账号和办理离职。
- 技师手机端首次激活、日常登录、账号不可用提示和退出登录。
- 账号状态在管理端技师列表中的可读展示。
- 凭证、旧会话、状态变更和权限失败的审计。
- 后端服务端权限、门店隔离、幂等和回归测试。

### 本期不包含

- 技师公开注册、手机号验证码、自助找回密码。
- 账号共享、公共 PIN、扫码免密登录。
- 技师排班、换技师、提成计算、结算、改价或会员操作。
- 物理服务位的开关、派单、离位、清洁和资源释放。
- 删除技师档案或清理历史顾客数据。

## 方案比较

### 方案 A：账号 + 密码 + 店长重置（采用）

店长创建档案并开通账号，技师首次用一次性凭证设置密码，日常用账号和密码登录；密码遗忘时由店长重置。该方案不依赖短信供应商，适合内部员工和门店现场，操作责任清晰且便于审计。

### 方案 B：账号 + 手机验证码

减少密码管理，但需要可靠的手机号归属、短信供应商、费用和网络依赖；员工换号或共用手机号时会削弱身份追责。本期不采用。

### 方案 C：公共 PIN 或共享二维码

现场操作看似简单，但无法确认实际操作者，停用和离职也无法可靠阻断共享凭证，不满足最小权限和审计要求。本期不采用。

## 角色与数据模型

### `Technician` 业务档案

继续保存姓名、编码、技能、等级、提成配置、门店归属和在岗状态。技师状态仍与登录状态分离：在岗、服务中、休息、离职描述业务可用性，不能单独作为登录凭证。

### `Staff` 登录身份

继续保存全局唯一的 `username`、密码哈希、角色、门店和 `technician_id`。技师账号必须满足：`role=technician`、存在 `technician_id`、`store_id` 与技师档案一致。账号状态使用现有 `active`、`invited`、`disabled` 语义。

为使重置、停用和恢复立即撤销旧 JWT，会给 `Staff` 增加递增的凭证版本字段 `credentials_version`，默认值为 1。签发 JWT 时带上版本；每次重置、停用、恢复、离职和重新开通均递增版本，服务端校验不一致即拒绝请求。

### `TechnicianInvite` 激活凭证

复用现有邀请表，增加用途字段 `purpose`，取值为 `activate` 或 `reset`。同一技师同时只保留一条有效记录；生成新凭证时使旧记录失效。数据库只保存 SHA-256 哈希，凭证明文只在店长操作成功响应中展示一次，有效期 24 小时，使用后写入 `used_at`。

### 账号状态展示规则

| 展示状态 | 判断条件 | 可执行操作 |
| --- | --- | --- |
| 未开通 | 有技师档案，无有效 `Staff` 或无有效邀请 | 开通登录 |
| 待激活 | `Staff.status=invited` 且邀请未使用、未过期 | 重新开通、办理离职 |
| 正常 | `Staff.status=active` 且技师未离职 | 重置登录、停用、办理离职 |
| 停用 | `Staff.status=disabled` 且技师未离职 | 恢复账号、重置登录、办理离职 |
| 离职 | `Technician.status=resigned`，关联账号停用 | 返聘并重新开通 |

## 用户流程

### 新入职与首次激活

1. 店长在管理端新建技师档案。
2. 店长点击“开通登录”；系统创建或复用绑定的 `Staff`，账号使用稳定的系统账号 `tech-{technician_id}`，并生成 `activate` 凭证。
3. 管理端只显示一次账号、激活凭证和失效时间；不显示或返回密码。
4. 技师访问 `/technician/`，进入“首次激活”并提交激活凭证和新密码。
5. 服务端校验凭证未使用、未过期、门店和对象关联一致，写入密码哈希、将账号改为 `active`、标记凭证已使用，写入激活审计并签发新会话。

### 日常登录

1. 技师访问手机端 `/technician/`。
2. 使用账号和密码调用现有员工登录接口 `/api/v1/admin/login`。
3. 服务端只允许 `active`、已绑定技师档案且门店关联正确的技师身份登录。
4. 登录成功进入今日服务；管理端员工或店长账号不得借此入口读取技师数据。

### 店长重置登录

1. 店长在技师列表点击“重置登录”，确认后端对象和本店范围。
2. 服务端递增 `credentials_version`，撤销未使用的旧凭证，生成 `reset` 凭证并写入审计。
3. 管理端一次性展示新凭证和失效时间；技师使用同一手机端流程设置新密码。
4. 重置前签发的 JWT 立即失效；重置不改变技师业务状态和历史数据。

### 停用与恢复

- 停用前要求店长确认；服务端将 `Staff.status` 置为 `disabled`，递增凭证版本并写审计。已有会话和新登录均被拒绝，技师档案及历史业务保留。
- 恢复仅适用于未离职技师；服务端将账号置为 `active`，递增凭证版本并写审计。原密码保持不变，店长可随后单独执行重置。
- 停用或恢复不改变服务位状态，不结束服务，不释放智慧宝资源。

### 办理离职与返聘

- 办理离职前检查该技师是否仍有 `assigned`、`ready` 或 `in_service` 任务；存在任务时拒绝操作并提示先完成交接。
- 离职成功后将 `Technician.status` 置为 `resigned`、关联 `Staff.status` 置为 `disabled`，递增凭证版本并记录离职原因和操作者。
- 离职不删除技师档案、服务单、顾客画像或审计；技师端所有接口立即拒绝访问。
- 返聘使用原技师档案，不新建重复档案。店长执行“返聘并重新开通”后，将业务状态恢复为在岗、生成新的 `activate` 凭证并要求设置新密码；旧密码和旧会话均不复用。

## 接口契约

### 已有接口继续使用

- `POST /api/v1/admin/login`：账号密码登录；返回 Staff 快照和 JWT。
- `POST /api/v1/technician/activate`：激活或重置凭证换取新密码和会话。
- `GET /api/v1/technician/me`：返回当前技师与门店范围内的最小资料。

### 管理端接口

- `POST /api/v1/admin/v2/technicians/{id}/invite`：开通登录，幂等返回当前有效激活凭证；已正常账号不得重复开通。
- `POST /api/v1/admin/v2/technicians/{id}/reset-login`：仅店长、本店范围；生成 `reset` 凭证并撤销旧会话。
- `POST /api/v1/admin/v2/technicians/{id}/disable`：停用登录身份，保留业务档案。
- `POST /api/v1/admin/v2/technicians/{id}/restore`：恢复未离职技师的登录能力。
- `POST /api/v1/admin/v2/technicians/{id}/resign`：校验无进行中任务后办理离职。
- `POST /api/v1/admin/v2/technicians/{id}/rehire`：恢复原档案并生成新的激活凭证。

所有写接口必须：

- 使用服务端 `_current_staff` 校验店长角色和当前门店。
- 再次校验目标技师、Staff、邀请记录的门店一致性。
- 支持请求幂等键或等价的状态幂等；重复请求不得重复改变状态或产生重复业务审计。
- 不接受客户端指定 `store_id`、`staff_id`、`technician_id` 作为权限依据。
- 返回结构化错误码，便于管理端显示“账号已正常、存在进行中任务、账号已离职”等原因。

## 管理端与手机端交互

### 管理端技师列表

- 删除按钮改为账号状态列和生命周期操作菜单。
- 每行显示姓名、编码、技师业务状态、登录状态、账号和最近状态变更时间。
- “开通登录”和“重置登录”成功后弹出一次性凭证；弹窗明确“仅显示一次”和过期时间，并提供复制按钮。
- “停用、恢复、离职、返聘”均使用二次确认，展示影响范围和不可逆的数据保留规则。
- 离职技师仍可查询历史记录，但不能被物理删除。

### 手机端登录与激活

- `/technician/login` 默认显示账号、密码输入和登录按钮。
- 对 `invited` 状态提供“首次激活”入口，字段为激活凭证、新密码、确认密码。
- 对停用、离职、过期凭证显示明确的联系店长提示，不泄露其他门店或账号存在性信息。
- 登录态失效时清理本地令牌并返回登录页；不自动降级到管理端。

## 权限、隐私与审计

- 技师只能访问当前门店、本人完成当前服务所必需的数据；不得查看全店顾客搜索、联系方式、经营分析、其他技师任务或提成数据。
- 店长只能操作自己门店内的技师；跨门店 ID 统一按不存在处理，避免泄露对象存在性。
- 密码使用现有 PBKDF2 哈希保存；激活凭证使用哈希保存；任何响应、日志和审计 detail 不写入明文密码或凭证。
- 登录失败继续使用现有 10 分钟内存限流；重置后旧密码和旧 JWT 均不能继续使用。
- 审计至少覆盖 `invite_technician`、`activate_technician`、`reset_technician_login`、`disable_technician_login`、`restore_technician_login`、`resign_technician`、`rehire_technician`，包含操作者 Staff、门店、技师、Staff、原因和结果状态。

## 错误处理

- 激活凭证不存在、已使用或过期：返回统一的“激活凭证无效或已过期”，不泄露具体记录。
- 店长重复开通正常账号：返回幂等成功或结构化冲突，不能生成第二个 Staff。
- 停用已停用账号、恢复已正常账号、离职已离职技师：返回幂等当前状态，不重复写状态转换审计。
- 离职存在进行中任务：返回 409 和任务交接提示，不修改任何状态。
- 网络失败或超时：前端保留表单内容并允许重试；服务端依靠幂等键避免重复写入。
- 数据关联异常（Staff、Technician、门店不一致）：拒绝操作并记录安全审计，不尝试自动修复。

## 测试与验收

### 后端

- 店长只能操作本店技师；员工、技师、跨店账号均被拒绝。
- 新建档案后开通生成唯一 Staff 和一次性凭证；重复开通不产生重复身份。
- 凭证只能使用一次，24 小时后失效，激活后不能再次使用。
- 重置会撤销旧凭证、旧密码和旧 JWT；新密码激活后可以登录。
- 停用拒绝新登录和已有会话；恢复后按设计保留或重置密码行为正确。
- 离职存在进行中服务时失败；无进行中服务时停用登录并保留全部历史数据；返聘生成新凭证。
- 所有状态转换、幂等重放和权限失败均有正确审计且门店隔离。

### 管理端

- 技师列表不再提供物理删除，显示登录状态和可用操作。
- 开通、重置、停用、恢复、离职、返聘均有确认、成功反馈和错误提示。
- 一次性凭证不在刷新后再次显示，复制操作不改变凭证状态。

### 手机端完整链路

使用授权测试技师完成：

`店长开通 -> 技师首次激活 -> 手机登录 -> 查看任务 -> 确认服务 -> 服务结束 -> 填写顾客服务参考 -> 写入审计`

再验证：

`店长重置 -> 旧会话失效 -> 新凭证激活 -> 新密码登录`

测试不得对未经门店授权的真实营业订单执行确认、结束或顾客服务参考写入。

## 发布与回滚约束

- 本地测试、管理端生产构建和手机端链路测试全部通过后，才允许准备发布。
- 发布前读取服务器实际 `current` 和 release Manifest，以实际线上版本为基线，不假设历史 release 仍为当前版本。
- 如涉及数据库迁移，发布前必须完成数据库备份、迁移 head 校验和恢复演练记录。
- 发布后检查 Manifest、API 健康接口、技师入口、登录/激活接口和容器重启次数；失败时原子回滚到发布前 current。
- `docs/WORK-STATUS.md` 必须记录本地完成、生产发布状态、release 路径、验证结果和待门店现场验收事项。
