# 技师端顾客画像 v3 与本人服务历史设计

日期：2026-09-05  
状态：待用户书面审阅  
范围：技师端、后端、管理端只读承接、数据迁移与合同测试

## 1. 背景与目标

现有 `schema_version=2` 只覆盖重点部位、避让部位、力度、温度、本次反馈和下次建议，适合作为最小服务参考，但不足以承载技师与顾客交流并完成约一小时服务后形成的连续服务记忆。

同时，技师端“历史服务单”目前读取旧 `service_orders`。技师实际确认和结束的 DIY 服务保存在 `position_occupancies`、`selection_sessions`、状态迁移、审计和画像记录链路中，导致页面可以进入但返回空列表。

本次目标：

1. 在不把技师端变成问卷的前提下，形成更完整、可确认、可分析的顾客服务画像。
2. 让技师看到本人真实服务过的历史，不看到其他技师的顾客历史。
3. 保留稳定编码、来源、确认、更正、门店隔离、审计和版本信息，为多门店分析打基础。
4. 不把正常交流记录包装成医疗诊疗，不因标签对顾客自动定价或作不利判断。

## 2. 产品原则

- **分层快记**：默认层 30–60 秒完成，更多维度按需展开；除“至少一项有效内容”外不强制填满。
- **点选优先**：结构化标签为主，顾客原话为辅；原话字段有长度限制。
- **来源明确**：字段保存 `customer_reported`（顾客自述）或 `technician_observed`（本次服务观察），不得把观察写成顾客事实。
- **顾客确认**：进入长期画像的记录必须展示摘要并由顾客确认；未确认内容只属于本次服务记录。
- **中性表达**：使用“偏高、适中、偏矮”“偏瘦、匀称、偏壮”等词，不使用羞辱性或诊断性标签。
- **服务相关**：只记录正常交流中与服务连续性、体验、安全或顾客偏好有关的情况。
- **最小可见**：技师只看本人当前服务所需的安全摘要和本人历史；管理端按门店权限读取，所有访问可审计。

## 3. 版本与顶层数据结构

- 数据结构：`schema_version=3`
- 标签体系：`taxonomy_version=service_reference_v2`
- v2 历史记录保持可读，不原地改写。
- v3 继续使用 `customer_profile_records` 的追加式记录、更正关系、门店/顾客/技师/选单关联、确认时间、幂等键和审计。

```json
{
  "customer_reported": {
    "personal_context": {},
    "work_lifestyle": {},
    "body_context": {},
    "service_preferences": {},
    "communication_preferences": {},
    "consumption_preferences": {},
    "service_related_context": {}
  },
  "technician_observed": {
    "session_response": {},
    "adjustments": []
  },
  "next_visit": {},
  "customer_confirmed": true
}
```

后端提供版本化只读标签字典；技师端和管理端不再各自维护同一套编码文案。

## 4. 标签维度

### 4.1 默认展开：本次最常用

- 本次重点：肩颈、背部、腰臀、手臂、腿部、膝周、腹部、头部、足部、整体放松。
- 避开或谨慎：使用相同身体区域，但不包含“整体放松”。
- 力度：轻柔、适中、偏强；支持“开始/结束”两次选择以表达中途调整。
- 温度：偏低、适中、偏高。
- 本次反馈：本次合适、调整后更合适、下次需调整。
- 下次安排：延续本次、重点调整、到店再确认。

### 4.2 按需展开：基础与外观背景

以下内容必须给顾客看过并确认，均允许“不记录”：

- 年龄段：18–24、25–34、35–44、45–54、55–64、65+。
- 身高印象：偏矮、适中、偏高；不要求测量具体身高。
- 体型：偏瘦、匀称、偏壮；不记录带评价色彩的称呼。
- 发量：较少、适中、较多；仅在头部相关服务或顾客主动讨论时出现。
- 职业场景：久坐办公、久站服务、经常驾驶、体力劳动、照护家庭、自由职业、退休、其他；不记录单位和具体职务。

### 4.3 按需展开：生活与身体使用场景

- 久坐、久站、经常驾驶、体力活动较多。
- 运动频率：少、每周 1–2 次、每周 3 次及以上。
- 睡眠感受：良好、一般、较差。
- 疲劳时段：上午、下午、晚间、不固定。
- 本次诉求：放松、久坐后舒缓、久站后舒缓、运动后恢复体验、睡眠体验、日常保养、其他。

这些是顾客的生活与感受描述，不生成疾病或健康结论。

### 4.4 按需展开：正常交流中提到的相关情况

允许记录顾客主动提到、与本次服务有关的情况：

- 长期身体情况被提及。
- 近期不适、旧伤或近期恢复情况被提及。
- 皮肤敏感或接触偏好被提及。
- 正在用药被提及。
- 孕期或产后阶段被提及。
- 其他需在本次或下次服务前再次确认的情况。

每项只保存“顾客自述”来源、标准分类、可选 100 字原话、确认时间和“下次需再次确认”标记。技师不得新增诊断、疗效判断、停药建议或治疗方案。顾客确有说出疾病名称、药品名称或孕产阶段时，可在顾客确认的原话中保留，但不自动拆成疾病画像或算法特征。

### 4.5 按需展开：服务过程反应

- 放松过程：较快、逐渐、始终较紧张。
- 力度接受：稳定、需要减轻、需要加强、多次调整。
- 温度反应：稳定、需要调低、需要调高。
- 服务节奏：偏慢、适中、偏快。
- 本次主观结果：明显放松、有所放松、变化不明显、顾客希望下次调整。
- 中途调整区域及调整方向。

只描述本次可观察行为和顾客反馈，不写“经络堵塞”“湿气重”等不可验证结论。

### 4.6 按需展开：沟通与消费偏好

- 沟通：喜欢安静、适度交流、主动聊天、动作前说明、称呼偏好。
- 项目介绍：不主动介绍、需要时说明、愿意了解。
- 决策关注：价格、品质、环境、效率、固定技师、固定时段。
- 预算倾向：实惠优先、平衡、体验优先、未表达。

不询问或保存具体收入、单位收入、资产或负债。顾客在交流中提到收入，只转化为其本人确认的预算/决策偏好，不保留金额。这些字段不得用于差别定价。

## 5. 交互流程

1. 技师结束本人服务后打开“本次服务参考”。
2. 页面先展示 6 组高频快选，并显示“更多服务记忆”折叠入口。
3. 展开后按“基本情况、生活工作、相关情况、过程反应、沟通消费”分组；各组显示已选数量。
4. 支持从上次已确认记录复制偏好类字段，但身体情况、用药、孕产和本次反应不得直接沿用，必须重新确认。
5. 保存前生成一屏中文摘要，技师当面请顾客核对；顾客可选择“确认”“修改”或“本次不保存为长期画像”。
6. 保存成功后显示“已记录到本次服务”，并允许在短时间内发起追加式更正，不覆盖旧记录。

## 6. 本人服务历史

### 6.1 权威关联

给 `position_occupancies` 增加可空的 `serviced_by_technician_id`：

- 首次确认服务时绑定当前技师。
- 服务结束必须由同一技师完成；如现场业务允许换技师，后续另建显式交接记录，不静默改写。
- 释放服务位后仍保留该字段，作为历史归属。
- 新增 `(store_id, serviced_by_technician_id, actual_service_end_at DESC)` 复合索引。

迁移时从已成功的技师确认/结束状态迁移和审计记录反查 `staff.technician_id`。只有同一占用能唯一确定一名技师时才回填；无法确认的旧数据保持空值，不归入任何个人历史。

### 6.2 API

新增技师专用只读接口，不复用管理端门店级 `service-orders`：

`GET /api/v1/technician/service-history?page=1&page_size=20&profile_status=all`

服务端强制使用当前登录技师 ID，不接受客户端传入 technician_id。返回：

- 占用/选单标识、服务日期、开始/结束时间和时长。
- 服务位名称与顾客脱敏名称。
- 项目名称快照，不返回价格、联系方式或会员资产。
- v2/v3 服务参考安全摘要、确认状态和是否待补记。

### 6.3 页面

- 默认按最近服务排序。
- 筛选：全部、待补记、已确认。
- 卡片展示日期、服务位、项目、时长、脱敏顾客、画像摘要。
- 点击只读详情；仅本人刚完成且尚未记录的服务提供“补充快记”。
- 空状态区分“本人尚无已完成服务”“旧记录无法确认服务技师”“加载失败”，不再统一显示“暂无服务单”。

## 7. 权限、确认与分析边界

- 技师只能写本人完成的服务、读取本人历史，并在活动服务中读取该顾客最近一次已确认安全摘要。
- 管理端可在本店查看完整历史和更正链，但相关情况原话默认折叠并记录访问审计。
- 算法默认只使用稳定结构化编码、版本、来源和确认状态；自由原话、疾病名、药品名、孕产描述和预算相关原话不进入训练或自动分群。
- 禁止根据身体、年龄、疾病、用药、孕产、收入或推断消费能力进行差别定价、拒绝服务或营销施压。
- 顾客可撤回长期画像确认；撤回后不再用于下次摘要或分析，审计记录保留最小必要事实。

## 8. 错误处理

- 未关联本人已完成服务：拒绝写入并返回明确业务码。
- 标签版本不匹配：前端刷新后端字典，不静默丢弃字段。
- 重复提交：同一幂等键和相同内容返回原结果；内容不同返回 409。
- 历史关联不确定：不猜测技师归属，标记为不可归属旧数据。
- 顾客未确认：允许保存为本次服务观察，但不进入长期摘要和跨次分析。

## 9. 测试与验收

- 合同测试覆盖所有编码、字段来源、确认状态、未知字段拒绝和版本兼容。
- 权限测试覆盖跨店、跨技师、未完成服务、伪造 technician_id 和敏感原话读取。
- 迁移测试覆盖唯一回填、多人冲突不回填、索引和单一 Alembic head。
- 前端测试覆盖默认快记、折叠分组、确认摘要、未确认保存、更正、历史筛选和三种空状态。
- 生产前完成 390×844 真机演练：确认服务、结束、完整/快速记录、顾客确认、历史出现、刷新、重复提交、断网恢复和审计。

## 10. 发布顺序

1. 后端模型、迁移、v3 校验、字典和本人历史接口。
2. 技师端分层快记、确认摘要和本人历史页面。
3. 管理端 v3 只读展示与最小门店聚合。
4. 备份与恢复演练、迁移、Manifest、原子发布、线上权限和移动端验收。

本轮不建设数据仓库、推荐模型、自动技师匹配或营销自动化；先确保采集质量、确认率、历史可见和权限边界。
