# 服务位维修备注与展示顺序设计

## 目标

完成管理后台 PRD 中“服务位支持启用、停用、维修备注和展示顺序”的剩余配置能力。范围只覆盖 DIY 内的静态服务位配置，不改变占用、服务单、二维码绑定或智慧宝物理资源。

## 已有基础与数据边界

`rooms` 已有 `note`（最长 256 字）与 `sort_order`（整数）字段，服务位列表已按 `sort_order, id` 读取。因此本次不新增列、不做 Alembic 迁移：对实际服务位，`note` 作为维修备注，`sort_order` 作为展示顺序。

空间容器（`is_space_container=true`）不属于实际服务位，不能通过本能力更新。已有非服务位/空间容器的通用备注不在本功能页面展示或修改。

## 接口与权限

新增严格的服务位配置更新入口，只接受：

- `maintenance_note`：可省略；提交空字符串清空；最大 256 字。
- `display_order`：可省略；必须为不小于 0 的整数。

接口先按登录身份解析目标门店，再取得服务位；总部管理员可操作任意门店，店长只能操作绑定门店，普通员工拒绝。跨店目标以不存在处理，不泄露目标数据。空间容器和非服务位返回校验错误。请求不接受运营状态、占用、二维码或地图位置字段。

写入时将 `maintenance_note` 映射为 `Room.note`、`display_order` 映射为 `Room.sort_order`，且记录操作者、服务位和前后值的审计事实。启用/停用继续使用既有专用接口及其活动占用保护；本功能不因服务位当前被占用而改变或拒绝静态备注/排序配置。

## 管理端

服务位管理页为管理员和店长提供备注与顺序编辑入口；普通员工只保留现有只读看板和二维码查看，不显示或调用该入口。

服务位看板与配置列表均按 `sort_order`、再按稳定 ID 展示。维修备注只出现在有后台权限的管理界面，不下发到顾客扫码入口，不加入顾客、会员、价格、画像或经营分析数据。

## 错误与兼容

- 空请求、未知字段、负数顺序和超长备注均返回 422。
- 未登录或普通员工沿用现有权限拒绝语义；跨店返回 404。
- 既有房间管理通用更新接口、二维码和运营状态接口维持兼容；前端仅为本次功能调用新严格入口。
- 旧 `note` 与 `sort_order` 的既有值原样读取，不进行数据重写。

## 验证

- 后端合同测试：字段映射、清空备注、顺序校验、未知字段拒绝、空间容器/非服务位拒绝、总部/店长/员工/跨店边界及审计。
- 管理端单元测试：权限入口、提交载荷、排序与备注展示；既有启停和二维码权限回归。
- 本地执行相应后端、管理端测试与类型检查，并执行 `git diff --check`。PR 后按 `tools/release/` 脚本等待可信检查；是否发布生产另按发布门禁决定。

## 非目标

- 不创建或控制智慧宝开房、开沙发、派钟、离位、清洁或物理资源释放。
- 不做拖拽平面图、批量排序算法、顾客端备注展示或现场营业验收。
