# 门店日常作业接口契约 v1

日期：2026-10-24。本分支隔离验收候选；未提交、合并、部署。现有角色、门店、价格与数据保留规则优先。

## 今日工作台与服务核对

- 店长工作台统计使用 `/admin/v2/manager/workbench`；在店服务使用 `/admin/live-service-position-map` 的当前占用与选单投影，不再用旧预约/支付订单列表冒充当前服务。
- 只读员工只使用既有安全选单投影，不请求店长工作台、服务待办、顾客反馈或员工管理接口。
- `/admin/order-reconciliation` 是只读核对，`/admin/order-reconciliation/sync` 才更新待办。两者均按当前员工门店限定最近30天数据；原有最大90天、1000条扫描和200条返回上限不变，不承诺全量或实时。
- 确认选单已有本选单的 `ServiceLine`，且关联同一选单的 `confirmed` 修订时，不因 `fulfillment_order_id` 为空报告 `missing_order`。异单修订关联不能冒充有效履约。此规则不创建旧订单，不改价、不改变履约状态。
- 历史订单存在时，原有缺选单、状态和金额校验继续保留。没有有效执行项目、也没有旧履约订单的已确认选单仍报告缺失。
- 旧待办不会自动关闭或删除；历史误报须人工核实并记录处理结果。新核对不等同历史数据修复。

## 服务待办

- 未处理 = `open` + `acknowledged`。知悉保留待办，关闭必须有处理说明。列表和操作保持当前门店与店长级权限限定。
- `assign` 与 `resolve` 在按门店/ID获取行锁后判断状态；重复指派给同一人返回已有结果、不新增审计。已关闭记录拒绝指派。
- 并发 `resolve` 仅一个请求成功；后到请求返回409，不能覆盖说明或增加第二条完成审计。表单保留输入并要求刷新确认状态。
- 解决待办仅记录核对结果，不修复原始选单、金额、服务状态。问题仍在时再次核对仍可能生成待办。
- 沿用当前 `acknowledge` 幂等与审计规则。不新增消息、财务接口、调度器、表或迁移。

## 验证要求

真实网络HTTP连接独立PostgreSQL；验证保存回读、受控行锁下并发重试、同店与跨店权限；ASGI/SQLite单元测试另列。前端必须显示真实错误和重试入口，不能用0和空列表代替请求失败。真机现场验收不由浏览器模拟代替。
