# 荷小悦 DIY 平台技术架构与接口契约

## 1. 架构原则

1. React/Vite + Ant Design 为现有管理端基线，采用 Ant Design Pro/ProComponents 信息架构；Refine 仅渐进式接管数据访问和资源 CRUD。
2. 共享 PostgreSQL 数据库，所有业务数据强制带 `store_id`，应用层与数据库行级策略双重隔离。
3. 总部主数据与门店运营状态分离，避免店长修改总部目录。
4. 智慧宝采用只读拉取适配器，DIY 不向智慧宝写入物理状态。
5. 所有状态变化通过显式命令接口完成，写请求必须幂等并可审计。
6. 采用向后兼容 API 和可回滚数据库迁移，不做一次性破坏性切换。

## 2. 系统分层

### 前端

- `admin-react`：总部与店长后台；
- 技师手机 Web：服务单和画像快记；
- ProLayout、ProTable、ProForm、权限路由和统一错误反馈；
- 当前门店上下文由登录身份、门店选择器和后端授权共同决定。

### 后端

- FastAPI API 层；
- 应用服务层：目录、媒体、门店运营、服务单、画像、报表；
- 领域层：价格快照、状态机、幂等、超时关闭和授权；
- 适配器层：会员、阿里云 OSS、智慧宝；
- 任务层：同步、媒体处理、异步导出和告警。

### 数据层

- PostgreSQL 主库；
- Redis 用于短期缓存、幂等键和任务协调；
- 阿里云 OSS 用于媒体；
- 备份存储与恢复演练环境。

## 3. 认证与授权上下文

每个请求解析并校验：

```json
{
  "user_id": "uuid",
  "role": "hq_admin|store_manager|technician",
  "home_store_id": "uuid|null",
  "active_store_id": "uuid|null",
  "authorized_store_ids": ["uuid"]
}
```

- 总部管理员可指定目标门店；
- 店长 `active_store_id` 必须属于绑定门店；
- 技师读取范围为主门店和授权门店集合；
- 技师写入必须使用当前服务门店；
- 所有资源查询自动追加门店条件；
- 越权返回统一 403/404，避免泄露资源是否存在。

## 4. 核心数据模型

- `stores`：门店主数据；
- `store_memberships`：用户与门店绑定及角色；
- `technician_store_authorizations`：技师同城跨店授权；
- `catalog_items`：商品、服务项目和加项主数据；
- `catalog_publications`：总部发布范围与版本；
- `store_catalog_states`：门店独立上架/下架状态；
- `media_assets`：OSS 对象、尺寸、校验、引用和软删除状态；
- `service_positions`：沙发、房间、床位和服务位；
- `position_qr_codes`：二维码版本、状态和绑定关系；
- `service_orders`：服务单状态与确认/结束信息；
- `service_order_snapshots`：项目、价格、会员身份和媒体快照；
- `customer_profiles`、`profile_records`、`customer_tags`：画像、快记和标签；
- `smartbao_sync_snapshots`、`smartbao_sync_cursors`：智慧宝只读快照与游标；
- `audit_logs`：不可变审计事件；
- `report_exports`：异步导出任务和下载凭证。

关键约束：历史快照不可被主数据更新覆盖；跨店授权和业务记录均带门店归属；媒体删除前检查引用；业务主键和外部 ID 使用唯一约束与幂等键。

## 5. API 约定

### 管理 API

- `/api/v1/admin/catalog/*`：总部编辑、发布和门店上下架；
- `/api/v1/admin/media/*`：预签名上传、确认、替换、排序、删除；
- `/api/v1/admin/stores/*`：门店、服务位和二维码；
- `/api/v1/admin/technicians/*`：技师账号和跨店授权；
- `/api/v1/admin/service-orders/*`：确认、结束和更正；
- `/api/v1/admin/profiles/*`：画像查看、记录、更正和作废；
- `/api/v1/admin/reports/*`：指标查询和异步导出。

### 命令接口

确认服务和结束服务均接受 `Idempotency-Key`，服务端保存命令结果。重复命令返回同一业务结果，不产生重复状态转移或审计事件。

### 媒体接口

1. 创建上传会话，返回对象键和预签名 URL；
2. 前端直传 OSS；
3. 调用确认接口执行格式、尺寸、病毒和引用元数据校验；
4. 业务对象引用媒体版本；
5. 删除执行软删除、引用检查和审计。

### 智慧宝适配器

统一返回内部模型，不让业务层依赖对方字段：

- `external_position_id`、`store_id`、`position_type`、`status`、`observed_at`；
- `external_technician_id`、`external_service_order_id`、`position_id`；
- `event_type`、`event_at`、`source_version`；
- 同步游标、拉取时间、错误码和新鲜度。

### 智慧宝后台只读审计得到的字段基线（2026-08-29）

本轮使用总部超级管理员会话对智慧宝后台进行只读核验，未执行任何业务写操作。以下字段可作为阶段 0 Mock Server 与 API 契约的初始基线，正式联调仍必须以智慧宝提供的 API 文档为准：

- 员工/技师：员工编号、姓名、性别、手机号、职位、技师分类、所属部门、是否技师、技师项目组、在职/离职状态、入职日期、最近编辑人和编辑时间；列表支持按手机号/编号/姓名、技师/非技师、级别、部门筛选。
- 房间/服务位：门店 ID、房间分区名称、房间编号、床位数、排序；已观察到“足浴房、SPA 房、娱乐房、茶室、炕床房、洗浴区、餐厅”等分区。房间状态至少包含打扫中、空房、开房、维修、已预约、休息中、休息超时、服务中、待检查。
- 顾客：昵称、性别、手机号、微信绑定、门店、客单价、消费金额、消费次数、上次消费、收益员工、积分、注册日期、顾客分类、会员阶段、顾客状态、标签、项目覆盖、获客渠道、备注；顾客配置还提供“流失风险客、静止客、有效客、优质客、新客、潜在会员、会员、临界会员”等阶段/状态规则。
- 项目：项目编号、名称、分类、上钟类型、首钟/加钟时长、是否副项、定价/最低价、加钟价、套餐销售、自助点单、启用/停用；支持改价、编辑和删除（DIY 仅拉取，不调用写操作）。
- 门店：后台可切换门店并显示门店名称与外部门店 ID；本次会话观察到外部 ID `1580752`、`1580751`、`1580993` 等门店上下文，名称存在重复，DIY 必须始终使用外部 ID 作为稳定键。

已确认但尚未获得 API 证据的字段：二维码/服务位二维码绑定与作废、技师实际派钟关系、智慧宝履约单 ID、开房/离位/清洁事件、分页与时间游标、认证和限流规则。上述字段在真实联调前均标记为 `contract_pending`，不得据此宣称生产可用。

## 6. 安全、可靠性与可观测性

- 生产月度可用性 99.9%；
- API 读 P95 ≤ 500ms，写 P95 ≤ 800ms；
- 管理端首屏 P95 ≤ 2.5 秒；
- RPO ≤ 15 分钟，RTO ≤ 2 小时；
- 审计日志和业务数据至少保留 3 年；
- 监控 API 错误率、延迟、任务积压、同步新鲜度、OSS 失败率和越权拒绝；
- 关键告警通知值班人员并保留处理记录；
- 敏感字段脱敏、最小权限、密钥轮换和下载凭证过期。

## 7. 兼容与迁移

- 新字段先扩展、回填、双读，再切换写入；
- 旧接口在过渡期保留兼容层；
- 每次迁移先备份、演练、校验，再灰度；
- 支持按 release 回滚前端和后端；
- 禁止直接删除生产历史数据和旧 API。
