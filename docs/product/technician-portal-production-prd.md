# 荷小悦技师端生产产品 PRD

版本：0.1（生产方案草案）  
日期：2026-08-26  
状态：待门店负责人、运营、财务、研发评审

## 1. 执行摘要

我们要建设一个与门店管理中台打通的技师端，为技师提供受控入职、登录、当日工作、服务操作、请假和离职后的账号处置能力，为店长和前台提供人员档案、排班/服务资格、权限、提成与审计管理。它解决当前“员工登录账号（Staff）”与“可排班技师档案（Technician）”分离、技师无法自助完成工作闭环、离职后权限和服务数据难以安全收口的问题，目标是让每一笔服务都有明确技师、状态和操作人，并在不牺牲顾客隐私与财务可追溯性的前提下降低前台协调成本。

**当前生产事实：**管理端地址为 `https://diy.hexiaoyue.com/admin/`；Staff 当前支持 `admin/staff` 两种角色、门店绑定、密码登录、12 小时令牌和失败锁定；Technician 当前是独立的技师/调理师档案，包含编码、姓名、手机号、等级、技能、提成规则和 `available/busy/off/resigned` 状态。当前没有公开注册、技师自有工作台、请假流程或离职结算闭环。

## 2. 问题陈述

### 谁遇到问题

- 一线技师：需要在手机或门店平板上确认当天任务、开始/完成服务、查看必要的顾客与项目上下文。
- 店长/管理员：需要建立人员档案、邀请账号、分配门店和技能、处理请假/停岗/离职，并保证权限及时回收。
- 前台：需要知道谁在岗、谁忙碌、谁可接单，避免把服务分配给离岗或已离职人员。
- 财务/运营：需要按已完成服务核对技师归属、提成和异常操作。

### 具体问题

当前系统把“能登录后台的人”和“被分配服务的人”建模为两个对象，缺少稳定关联及生命周期规则。技师可能只能依赖前台代操作；账号创建、密码交付、停用、离职和历史数据保留没有统一产品流程；请假期间仍可能出现在可分配列表；离职后令牌、排班、进行中服务和提成数据的处理边界不清。

### 痛点与影响

- **用户影响：**技师无法确认自己的任务和责任边界，依赖口头沟通，容易漏做、重复做或误操作。
- **门店影响：**前台承担大量代录入和协调，排班准确性下降；离职/换班时容易出现“账号还能用”或“服务无人负责”。
- **经营影响：**服务事实、技师归属、提成和审计链不完整，异常处理成本高。

### 证据与缺口

- 已验证：生产系统存在独立 `Staff` 与 `Technician` 模型；当前生产技师列表有 1 条用于 P0 验收的模拟档案。
- 已验证：生产 API 已支持员工密码登录、门店范围隔离、失败 5 次锁定 10 分钟、临时账号过期和审计日志基础设施。
- 🔵 **开放问题：**尚无真实技师使用量、代操作比例、请假频次、离职频次和服务异常基线，需要上线前补采。
- 🔶 **假设：**“受控邀请 + 技师自助日常操作”比开放注册更适合门店场景，因为技师必须先经过门店审核并绑定门店。

## 3. 目标用户与画像

### 主要画像：一线技师小悦

- **职责：**按排班完成泡脚、调理等服务，记录开始/完成和必要备注。
- **目标：**登录即看到当天工作；只操作分配给自己的服务；换班或异常时留下可追溯记录。
- **痛点：**不希望记复杂账号；不应看到其他顾客的无关隐私或经营数据；弱网环境下不应重复提交。
- **行为假设：**主要使用手机浏览器或门店共享设备，单次操作时间短、频率高。

### 次要画像：店长/管理员

负责邀请、启用/停用账号，维护技师档案、技能、等级、提成、排班和离职流程，处理异常和审计查询。

### 次要画像：前台员工

查看在岗与忙碌状态、进行服务位和订单操作；不能修改账号权限、提成规则或执行离职。

### Jobs-to-be-Done

- **功能工作：**我到店后能快速确认今天该服务什么，并准确完成每个服务状态。
- **情绪工作：**我希望系统明确记录“谁在何时做了什么”，避免因口头沟通背锅。
- **社会工作：**我希望店长和顾客看到的是专业、稳定、可交接的服务过程。
- 🔶 **假设：**技师端首屏应优先呈现“待开始/服务中/待完成”而不是经营报表。

## 4. 战略背景

### 业务目标

1. 建立可控的门店人员身份体系，支撑连续运营和多门店扩展。
2. 让服务操作从“前台代操作”转为“责任人直接确认”，提高服务事实完整度。
3. 将技师状态、技能、排班、提成和离职处置纳入同一审计链。

### 差异化定位

“门店现场服务责任人工作台”，重点不是通用 HR，而是把技师身份直接连接到服务位、服务单、顾客选单和提成事实。

### 为什么现在

生产系统已完成服务位、双床并行、服务完成、结算、离位和清洁闭环；如果没有技师身份与离职回收，闭环中的责任归属仍依赖前台人工。🔵 **开放问题：**是否需要在下一轮连续运营观察中将真实技师端作为必测路径，由运营负责人确定上线批次。

## 5. 解决方案概览

### 总体方案

采用“门店管理员创建/邀请，技师激活并登录，服务端按门店与角色授权”的模式。`Staff` 负责登录身份、权限和账号状态；`Technician` 负责业务档案、服务资格和提成；两者通过明确的一对一关联连接。技师端只暴露与本人任务和门店现场相关的能力，所有状态迁移由服务端校验并写入审计。

### 核心模块

1. **人员与账号：**创建技师档案、发送邀请、首次激活、重置密码、冻结/解冻、强制退出。
2. **技师登录：**账号密码登录、登录失败保护、短期/长期会话策略、设备退出；后续可接短信或 MFA。
3. **今日工作台：**查看本人待服务、服务中、已完成、异常待处理任务；显示项目、服务位、必要的顾客称呼和注意事项。
4. **服务操作：**接受/开始/暂停（如批准）/完成、备注、异常上报、交接；支持幂等键和弱网重试提示。
5. **请假与在岗：**提交请假、撤回、审批、紧急离岗；审批后自动影响可分配状态和排班。
6. **离职与回收：**设置生效时间、终止未完成排班、转移进行中服务、撤销会话、保留历史服务和财务记录。
7. **管理与审计：**技师列表、筛选、技能/等级/提成、账号状态、操作日志、导出和异常报表。

### 目标状态机

账号状态：`invited → active → suspended → resigned/disabled`。  
技师业务状态：`available ↔ busy/off`，离职后进入 `resigned`；`resigned` 不得被重新分配服务。  
请假单状态：`draft → submitted → approved/rejected/cancelled`。  
任何从 `active` 到 `suspended/resigned` 的变化都应立即使已有令牌失效或在下一次请求校验时拒绝。

### 关键流程

**入职注册：**管理员录入档案 → 生成一次性邀请链接/邀请码 → 技师设置密码并确认手机号 → 账号激活 → 绑定 Technician → 首次登录工作台。禁止无门店、无管理员审核的公开注册。

**登录使用：**输入账号密码 → 服务端校验门店、账号状态、临时有效期和失败次数 → 签发 Staff 令牌 → 加载本人 Technician 档案和当日任务 → 每个写操作带幂等键 → 成功后刷新状态与审计。

**请假：**技师选择日期/时段和原因 → 系统检查是否有进行中服务或冲突排班 → 提交审批 → 店长批准后标记 `off` 并从可分配列表移除 → 需要恢复时由管理员结束请假或技师按规则撤回。

**离职：**管理员确认生效时间和接替人 → 系统阻止未来分配、提示处理进行中服务和未结提成 → 到生效时间撤销会话、停用账号、将 Technician 设为 `resigned` → 历史订单、服务线、审计和提成快照只读保留。

## 6. 成功指标

### 主指标

**技师服务自操作完成率**：由技师本人完成的“开始服务 + 完成服务”服务单数 ÷ 全部已完成服务单数。

- 当前：🔵 **开放问题**，需从上线前 14 天生产日志建立基线。
- 目标：🔶 **假设目标**，首个完整运营月达到 ≥80%，第二个月达到 ≥90%。

### 次指标

- 账号激活率：受邀技师在 48 小时内完成激活，目标 ≥90%。
- 首次登录成功率：目标 ≥95%。
- 服务状态漏记率：目标 ≤2%。
- 请假审批时效：工作时间内 P95 ≤15 分钟。
- 离职权限回收时效：生效后 ≤1 分钟内旧令牌不可用。
- 服务交接异常率：目标 ≤1%。
- 技师端关键操作接口 P95 延迟：≤800ms（不含网络重试）。

### 护栏指标

- 顾客隐私越权事件：0。
- 跨门店数据访问：0。
- 重复状态迁移或重复提成记账：0。
- 前台核心闭环成功率不得因技师端上线下降超过 2 个百分点。

## 7. 用户故事与需求

### Epic 假设

我们相信，将 Staff 身份与 Technician 档案关联，并提供技师本人可用的工作台、请假和离职回收流程，会把服务责任从前台人工转为技师直接确认，提升服务事实完整度并降低交接异常；上线后以“技师服务自操作完成率”和权限回收时效验证。

### 7.1 注册、邀请与账号安全

**US-01 管理员创建技师档案**  
作为店长，我想创建包含编码、姓名、手机号、等级、技能和提成规则的技师档案，以便后续排班和核算。

验收标准：

- [ ] 技师编码在全局唯一；姓名、编码、门店为必填。
- [ ] 技能只能选择本门店已发布项目或配置项。
- [ ] 创建操作写入审计，记录操作者、门店、字段变更前后值。
- [ ] 仅 `admin` 可创建、编辑、删除或修改提成；`staff` 只能查看必要字段。

**US-02 管理员邀请技师激活账号**  
作为店长，我想向已审核的技师发送一次性邀请，以便技师自行设置密码而不暴露管理员密码。

验收标准：

- [ ] 邀请绑定唯一 Technician、门店和过期时间；默认有效期 🔶 **假设为 24 小时**。
- [ ] 邀请链接只能使用一次，重发会使旧链接失效。
- [ ] 技师设置密码后 Staff 状态变为 `active`，完成一对一关联。
- [ ] 邀请、激活、失败和撤销均可审计；链接中不出现明文密码。
- [ ] 不提供公开注册入口；手机号已被其他门店占用时阻止激活并提示管理员处理。

**US-03 技师登录与找回**  
作为技师，我想使用账号密码登录，在忘记密码时通过受控方式找回，以便不中断工作。

验收标准：

- [ ] 登录成功后仅返回本门店和本人可见数据；令牌包含 Staff 身份，不接受顾客令牌调用管理 API。
- [ ] 连续 5 次失败后锁定 10 分钟；错误提示不泄露账号是否存在。
- [ ] 账号被冻结、离职或邀请过期时不能登录；已有令牌在请求时被拒绝。
- [ ] 找回密码必须由管理员重置或已验证手机号完成；重置后撤销旧会话。
- [ ] 支持主动退出当前设备和“退出所有设备”。

### 7.2 工作台与服务操作

**US-04 查看今日工作**  
作为技师，我想看到当天分配给我的服务，以便按顺序完成工作。

验收标准：

- [ ] 默认只展示本人、当前门店、当前营业日的任务。
- [ ] 每项显示服务位、项目、预计时长、当前状态和必要顾客称呼；不显示无关手机号、支付敏感信息。
- [ ] 状态至少区分待开始、服务中、待完成、已完成、异常。
- [ ] 任务变更、换班或撤销后刷新可见，不能依赖本地缓存作为最终事实。

**US-05 开始与完成服务**  
作为技师，我想直接确认开始和完成，以便系统记录真实服务时间和责任人。

验收标准：

- [ ] 只有被分配给当前 Technician 且满足前置状态的服务可操作。
- [ ] 开始/完成接口幂等；重复点击不会生成重复事件、重复提成或重复通知。
- [ ] 完成前可填写结构化备注和异常原因；必填项由项目规则决定。
- [ ] 操作成功后服务位、服务单、技师状态和审计日志一致更新。
- [ ] 弱网或超时显示“结果待确认”，重新查询后再允许重试。

**US-06 异常与交接**  
作为技师，我想上报迟到、顾客未到、身体不适或需要换班，以便前台及时处理。

验收标准：

- [ ] 异常类型为枚举，支持文字备注和附件 🔵 **开放问题：**是否需要照片/语音。
- [ ] 提交异常后任务进入待前台处理，不自动伪造完成状态。
- [ ] 交接必须指定接替技师或前台确认，保留原技师和接替技师。
- [ ] 进行中服务禁止无审批转移；紧急强制释放需要管理员权限和原因。

### 7.3 请假、在岗与离职

**US-07 提交请假**  
作为技师，我想提交请假时段和原因，以便店长安排替班。

验收标准：

- [ ] 不能提交过去时段；同一技师重叠请假不可提交。
- [ ] 与已有排班/服务冲突时明确列出冲突任务，不能静默覆盖。
- [ ] 提交后状态为 `submitted`，技师可在审批前撤回。
- [ ] 店长审批、驳回需填写可选备注，并向技师显示结果。

**US-08 审批请假与调整在岗状态**  
作为店长，我想审批请假并看到受影响的排班，以便保证门店有人接替。

验收标准：

- [ ] 审批前展示冲突任务、接替建议和预计影响。
- [ ] 批准后技师从可分配列表移除，状态/排班变更可追溯。
- [ ] 已有进行中服务不能仅靠批准请假强制结束，必须走交接或异常流程。
- [ ] 前台和技师端在刷新后看到一致状态。

**US-09 办理离职**  
作为店长，我想设置离职生效时间并完成权限、排班和服务交接，以便安全结束劳动关系。

验收标准：

- [ ] 离职前展示未来排班、进行中服务、未结提成和待处理异常清单。
- [ ] 未处理清单必须由管理员确认接替人、释放或保留原因后才能提交。
- [ ] 到生效时间 Staff 账号不可登录，所有旧令牌请求返回 401；Technician 状态为 `resigned`。
- [ ] 离职后不能新建分配、开始服务或修改历史服务事实；财务快照和审计仍可读。
- [ ] 支持撤销“预定离职”但不允许恢复已完成的财务结算而不留痕。

### 7.4 管理、权限与审计

**US-10 人员管理台**  
作为店长，我想按状态、技能、等级和在岗情况筛选技师，以便快速排班和处理异常。

验收标准：

- [ ] 列表区分账号状态和业务状态，避免把“账号 active”误认为“可接服务”。
- [ ] 可查看关联关系、最近登录、最近服务、请假和离职信息，但按角色脱敏手机号等字段。
- [ ] 删除改为软删除/离职，不物理删除有历史服务的 Technician。
- [ ] 所有跨门店查询按当前登录 Staff 的 `store_id` 强制过滤。

**US-11 权限与审计**  
作为运营负责人，我想知道谁在何时执行了什么操作，以便追责和复盘。

验收标准：

- [ ] 权限最小化：技师仅本人任务和本人请假；前台可运营操作但不可改权限/提成；管理员可管理本店人员。
- [ ] 关键动作（邀请、激活、登录失败、重置密码、开始/完成、请假审批、离职、强制释放）写入不可篡改审计。
- [ ] 审计记录包含 actor、门店、实体、前后状态、原因、请求幂等键和时间。
- [ ] 审计查询支持按技师、操作类型、日期和服务单过滤并导出。

### 约束与边界情况

- 技师端必须移动端可用，支持主流 Chromium/Safari 最近两个大版本。
- 所有写操作服务端校验门店、角色、Technician 关联和状态版本；前端隐藏按钮不构成权限控制。
- 并发操作采用版本号/幂等键，双床、多人和前台/技师同时操作不能互相覆盖。
- 账号与 Technician 解除关联时必须由管理员执行并审计；历史服务不改变原责任人。
- 数据库或短信服务暂时不可用时，不得显示“已成功”；提供可重试的明确状态。

## 8. 本期不做

- 公开自助注册或无审核加入门店：会造成冒用和跨店数据风险。
- 复杂 HR（合同、工资、考勤打卡、社保）：先聚焦服务责任和账号生命周期。
- 技师查看完整顾客档案、支付详情或全店经营报表：遵循最小必要原则。
- 自动计算并发放工资/提成：本期只记录可核对的服务与提成快照，财务结算规则另行立项。
- 多门店自由切换：首期账号绑定单一门店；跨店调动走管理员迁移流程。
- 实时聊天、视频培训、在线请假证明 OCR：待核心流程稳定后评估。

## 9. 依赖、风险与发布门禁

### 依赖

- 后端：Staff、Technician、服务单/服务线、服务位、审计日志和通知能力；新增关联表、邀请令牌、请假单、会话撤销记录。
- 前端：管理端新增邀请/生命周期页面，新增技师移动工作台；复用现有管理端 API 拦截器和门店范围能力。
- 运维：短信或邮件邀请通道、密钥轮换、会话撤销存储、监控告警和每日异常报表。
- 运营：角色权限矩阵、请假政策、离职清单、提成结算责任人和客服话术。

### 风险与缓解

- **价值风险：**技师仍让前台代操作。缓解：先选择 1 家门店、3–5 名真实技师灰度，按自操作完成率和访谈迭代。
- **可用性风险：**现场弱网导致重复点击或误以为成功。缓解：幂等键、结果待确认态、离线只读缓存、真实设备演练。
- **可行性风险：**Staff 与 Technician 一对一关联、历史数据迁移不完整。缓解：迁移脚本先在备份恢复库演练；无匹配档案的 Staff 不自动猜测。
- **安全风险：**离职后旧令牌仍有效或跨店越权。缓解：每次请求校验账号状态与门店；令牌撤销黑名单/版本号；自动化越权测试。
- **经营风险：**请假/离职状态影响正在服务的顾客。缓解：提交前展示冲突；强制释放必须管理员确认、填写原因并产生审计。
- **合规风险：**顾客与技师个人信息暴露。缓解：字段分级、脱敏、最小权限、访问审计和数据保留策略。

### 生产发布门禁

1. 在生产备份恢复库完成数据库迁移和回滚演练。
2. 完成管理员邀请、技师激活、登录、开始/完成、请假审批、离职回收的端到端测试。
3. 验证离职生效后旧令牌立即失效、历史服务仍可读、提成快照不变。
4. 完成跨门店、并发双床、重复提交、断网重试和刷新恢复演练。
5. 真实设备验收：至少 2 种手机浏览器 + 门店平板；核心接口和错误告警已接入监控。
6. 灰度门店连续观察 7 天，无 P0/P1 权限或财务一致性问题后再扩大范围。

## PRD 自评

### 最强部分

第 7 节“用户故事与验收标准”：将注册、登录、服务、请假、离职和管理拆成可测试的业务切片，并明确服务端状态与审计要求。

### 最弱部分

第 6 节指标基线和第 10 节运营政策仍缺真实数据与门店确认；当前目标值属于 🔶 **假设**，不能直接作为发布承诺。

### 最高风险假设

| 假设 | 风险 | 验证方式 |
|---|---|---|
| 技师愿意本人完成服务操作 | 采用率不足，前台负担不降 | 3–5 名真实技师 7 天灰度 + 访谈 |
| 受控邀请优于公开注册 | 入职激活率低 | 对比短信邀请与现场邀请码的激活漏斗 |
| 24 小时邀请有效期合理 | 邀请过期造成门店阻塞或安全窗口过长 | 观察激活时延和重发率 |
| 离职生效后 1 分钟内回收权限可实现 | 旧令牌越权 | 自动化集成测试 + 生产演练 |

### 推荐下一步

先由店长、前台、真实技师各访谈 2 人，确认权限矩阵、请假政策、顾客可见字段和提成结算时点；随后在生产备份恢复库完成 Staff–Technician 关联与离职回收的数据迁移演练，再进入单店灰度。
