# 按服务项目记录与预览顾客要求

状态：文字及可操作原型已获用户确认；招牌草本泡 v6 本地实现与服务器隔离验证完成，待合并发布。落地契约见 `../contracts/project-service-record-v1.md`；其他项目模板保留后续迭代，不改菜单配置。

## 1. 摘要

技师服务后快速记录，下一次服务前快速预览，以改善顾客体验、传递有效服务经验，并为长期运营保留可靠事实。采用项目相关点选加可选文字，不再使用纯文字优先方案或通用标签问卷。

## 2. 角色

技师负责实际记录与当面确认；下一位有权限的技师负责按本次沟通使用参考；门店负责人组织试点。管理端开发与技师端开发共同落实跨技师安全读取合同。具体试点人员未指定。

## 3. 背景

依据用户提供的门店项目单，以及逐轮确认的招牌草本泡文字原型。项目包括泡脚、推拿、SPA、采耳、头疗、足部精修、拔罐、刮痧和套盒等，不应共用一份按摩力度表。

菜单存在列错位，荷小推标称时长与流程时长不一致；本轮不修正价格、时长或项目配置。原型示例不是顾客真实数据。

## 4. 目标

记录可快速完成，读取后能知道本次应该确认什么。用相同情景验证点选与文字操作，不把点击数等同效率。

试点建议目标：5 位技师中至少 4 位无需讲解完成典型记录并找回；不得发生错误顾客关联、未保存被误认为已保存。目标不是实测结果。长期运营依赖事实积累，不宣称本次改版提高复购。

## 5. 场景

服务前：打开服务单即可看到有权限的历史参考。
服务后：仅记录明确表达、实际操作、明确反馈；空白不等于没有或满意。
再次到店：看日期和来源，确认要求是否变化，不机械沿用旧偏好。

## 6. 价值与范围

常见情况点选，特殊情况补一句，降低组织语言与寻找标签的负担。一处调整成为一条完整记录，不拆散在多个独立栏目。

第一版必须包含记录、权限允许的服务前预览、历史和纠正。店长待办、AI 推断、营销分群、人口属性问卷不纳入本轮。历史数据不删除。

## 7. 已确认交互与文案

### 服务前

标题：本次服务。展示真实项目名称与配置时长。

“上次服务参考”按泡脚、肩部按摩、休息与聊天等实际事项展示完整句子，例如“顾客说水有点烫，调低后表示合适”。显示日期、记录来源及“上次的要求可能有变化，请以本次沟通为准”。仅显示权限允许且确实存在的内容，不罗列未记录字段。

### 服务后：招牌草本泡模板

标题：记录本次服务。提示：只选顾客明确表达的情况，不必每项填写。

1. 泡脚时，顾客对水温有要求吗？选项：希望低一点／现在就合适／希望高一点。选择调整要求后，同页显示“调整后，顾客怎么说？”：水温合适了／仍不合适；可不选。不把要求自动写成已调整。
2. 按摩时，哪些地方需要调整？点击“记录一处”，同页呈现：哪个部位、侧别、顾客要求、本次处理、顾客反馈。顾客要求选项：轻一点／重一点／多按一会儿／不要按这里。本次操作独立选择，不能自动认定已执行。反馈：调整后合适／仍不合适，允许空白。删除只移除本次尚未提交的条目。
3. 热敷时，有什么需要记录？选项：顾客觉得太烫／顾客表示温度合适／顾客要求提前结束。不同时间可能出现不同反馈，不能把矛盾选项压成同时成立的单一偏好；发生调整时保留先后与实际处理。未实施热敷不填写。
4. 顾客想聊天还是休息？选项：想安静休息／愿意聊天。不得根据话多话少推断。
5. 还有其他需要记住的事吗？可选文字，支持键盘语音输入，不新增录音上传。文字按现有权限仅本人可见。

页面只有一次最终“保存记录”。全空可点“本次没有新情况”，不等于满意、未重新确认历史、不清除旧记录。未保存退出提示，失败保留表单与重试能力，成功才能显示已保存。

### 项目适配

泡脚模板只显示水温等相关环节；推拿关注部位与力度；SPA 增加实际涉及的精油要求；采耳、头疗、足护按实际服务环节设计，不能继承无关的泡脚、按摩问题。组合服务按实际环节去重。不得凭项目名推断已执行全部环节。

### 数据与权限

分开保存顾客要求、技师操作、顾客反馈，关联顾客、门店、服务单、技师、时间、模板版本及修订。未操作、未询问、未确认不能映射成否定值。

当前 v5 数据契约不一定承载完整的新语义；实现前核对并补齐合同与后端测试，不把不同部位的力度压成一个全局力度。跨技师读取须有明确门店、服务关联与最小字段权限，不能直接开放自由文本或身体自述。

匿名记录跟随本次服务，不把设备当作人的可靠身份。旧偏好不默认永久有效；更改有来源和时间，修订保留原版本。

### 文案验收

逐词检查标题、选项、提示及保存结果：谁说的、谁做的、对象是什么、何时发生。避免动作前说明、有效调整、接受情况等抽象术语；项目名称不改写成效果结论。不适应按门店流程当场处理，记录不是处理措施。

## 8. 交付与风险验证

先制作招牌草本泡可操作原型，验证水温调整、单部位调整、无明确反馈、空记录、保存失败、历史纠正及另一位有权限技师读取。通过后扩展其他项目模板，不直接批量复制文案。

用户价值假设：预览能改善服务，信心中，需用接手技师任务验证。易用性假设：项目化点选更快，信心中，需计时与观察误选。业务假设：不按字数考核仍认真记录，信心低，需试点。技术风险：跨技师与结构化变更，须合同测试验证，前端预览不能代替后端能力。

原型、实现、合同测试、服务器验证、生产发布分别报告。自动化通过不等于微信真机及门店验收。
