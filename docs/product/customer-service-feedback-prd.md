# 顾客服务结束后评价 PRD

- 版本：v1.0-draft
- 日期：2026-09-09
- 负责人：顾客端
- 状态：V1 顾客端本地实现完成，尚未发布；本文不代表已上线功能

## 1. 一句话定义

在服务**实际结束后**，让顾客用不被打断、可随时回来完成的方式表达体验；把评价沉淀为门店可行动的改善信号，而不是用于催评、强制好评或自动评价技师。

## 2. 背景与现状

现有顾客端已经具备以下基础：

- 服务完成页、`我的—待评价`、到店详情均可进入评价；
- 只有服务端存在权威服务结束时间时才可评价；同一选单重复提交不会创建第二条；
- 匿名顾客可使用原选单凭证，登录顾客仅能评价本人记录；
- 当前表单为默认五星、固定五个标签和最长 1000 字自由文本。

现状的主要问题不是“少一个入口”，而是评价任务缺乏明确的产品分层：默认五星会把“未选择”误记为好评；正负体验使用同一组标签，顾客难以快速说明问题；低分反馈没有明确的知情、转交和处理边界；评价入口与“再次选购”在服务结束后的优先级也未被定义。

## 3. 目标、非目标与原则

### 3.1 目标

1. 顾客在服务完成后 30 秒内完成一条有效评价，不被登录、领券或再次选购阻断。
2. 每条评价可可靠对应一笔已结束的服务记录，并可由门店在后续能力中识别需要改善的体验维度。
3. 让顾客在不评价时也能直接再次选购；评价是邀请，不是离店门槛。
4. 评价数据可用于体验改善和聚合分析，但不展示为公开点评、不自动影响价格、会员权益、提成或技师考核。

### 3.2 非目标

- 不做公开评论社区、榜单、分享裂变、返券/返现或“好评奖励”。当前停券策略不因评价恢复。
- 不在线支付、退款、理赔或处理医疗诊断；顾客端不写技师服务状态、服务位或物理资源状态。
- 首版不承诺实时人工回复，不将低分自动派单给技师。
- 不以评价代替投诉、紧急安全事件或线下结算异议处理。

### 3.3 体验原则

- **先结束、后邀请**：仅服务端确认结束后出现，绝不在提交选单或服务中提前索评。
- **先选择、后表达**：先明确星级，再根据体验呈现少量相关标签；文字始终选填。
- **不逼迫、不预设**：初始无星级；关闭、返回和再次选购都不判作已评价。
- **一事一评、一次一源**：一笔服务最多一条评价，服务端事实为唯一准绳。
- **私密、可解释**：说明评价用于改进服务；不在埋点中采集原文、手机号、令牌或健康隐私。

## 4. 用户、场景与任务

| 用户 | 典型场景 | 核心任务 | 成功标准 |
|---|---|---|---|
| 匿名到店顾客 | 服务结束，仍在项目完成页 | 给出简短感受，或直接再选项目 | 评价不要求手机号；再次选购可立即开始 |
| 登录顾客/会员 | 回家后进入“我的” | 找回待评价服务、核对记录、完成评价 | 仅可操作本人已结束记录 |
| 对体验不满意的顾客 | 觉得手法、沟通或环境不合适 | 用低负担方式说明问题，并自主选择是否希望联系 | 不被强迫公开、不过度收集隐私 |
| 门店负责人（后续能力） | 查看聚合体验信号 | 识别需要改善的维度并跟进 | 仅看到授权门店的必要信息与审计记录 |

## 5. 端到端流程

```text
技师/门店结束服务
        ↓（服务端写入权威结束时间）
顾客端刷新服务状态 → 可评价
        ├─ 服务完成页：评价本次服务 / 再次选购
        ├─ 我的：待评价任务 → 到店详情 → 评价
        └─ 记录详情：评价本次服务
        ↓
选择星级 → 选择相关标签（可选）→ 补充说明（可选）→ 提交
        ↓
服务端幂等保存 → 已评价结果 → 待评价数量、详情和列表同步更新
```

### 5.1 入口优先级

| 位置 | 呈现 | 行为 |
|---|---|---|
| 服务完成页 | 感谢区下的“评价本次服务”次级按钮；“再次选购/返回项目列表”保持可用 | 不自动弹窗，不阻断再次选购 |
| 我的首页 | 仅待评价数量大于 0 时显示任务卡 | 点击进入待评价筛选，不直接替顾客打开表单 |
| 到店记录与详情 | 未评价记录显示“去评价/评价本次服务” | 先展示该次项目、完成时间与价格记录，再进入表单 |
| 已评价记录 | 显示“已评价”状态 | 首版不提供二次提交或修改入口 |

关闭评价弹层后回到原页面与滚动位置。顾客选择再次选购时必须新建或恢复**独立的新选购**，不得复制旧项目、复用已结束会话或改变评价资格。

### 5.2 已确认的顾客文案预览

服务完成页以“再次选购”为主路径，并列提供评价入口：

```text
✓ 本次服务已结束
感谢本次体验

3号沙发 · 本次服务已完成

[ 再次选购 ]        [ 评价本次服务 ]
```

评价页初始文案：

```text
←             评价本次体验             ×

这次服务体验如何？
请选择评分

☆   ☆   ☆   ☆   ☆

可选：告诉我们哪些地方让您印象深刻
[ 手法专业 ] [ 力度合适 ] [ 沟通细致 ]
[ 环境舒适 ] [ 整体放松 ]

还有想告诉我们的吗？（选填）

                 [ 提交评价 ]
```

提交成功页：

```text

感谢您的评价

已记录到本次到店服务。
您的反馈会帮助我们持续改进体验。

[ 返回到店记录 ]       [ 再次选购 ]
```

低分场景保留“希望门店联系我处理”的关闭态开关；它必须由顾客主动打开，且在跨端跟进闭环确认前不可暗示实时回复或既有回访承诺。

## 6. 评价表单与内容策略

### 6.1 首屏

- 标题：`这次服务体验如何？`
- 先展示 1–5 星；初始为未选择，提交前必须显式选择一星级。
- 点击后立即显示对应的短文案：1 星“很不满意”、2 星“不太满意”、3 星“一般”、4 星“满意”、5 星“非常满意”。文字与颜色同时变化，不只依赖颜色。
- 星级控件与提交按钮的有效触控区不小于 44px；支持键盘与读屏标签。

### 6.2 标签

标签至多选 3 个，均选填；同一评价只保存枚举值，不允许前端自由添加标签。按星级分组，避免顾客在负面体验时看到“整体放松”这类不相干选项。

| 星级 | 标签候选（首版建议） |
|---|---|
| 4–5 星 | 手法专业、力度合适、沟通细致、环境舒适、整体放松 |
| 3 星 | 手法一般、力度需调整、沟通可更清楚、环境一般、项目预期不一致 |
| 1–2 星 | 力度不合适、沟通体验不好、等待较久、环境问题、项目与预期不符、其他问题 |

标签文案是体验描述，不包含疾病、疗效、身体敏感部位或对人员的人身评价。具体枚举须在实现前写入跨端契约并由运营、门店确认；不得由前端自行替换。

### 6.3 补充说明与低分关怀

- 补充说明为选填，最多 300 个汉字等效长度；输入框提示“请勿填写手机号、证件号或其他隐私信息”。
- 仅 1–2 星时额外展示“希望门店联系我处理”开关，默认关闭。打开前说明将把本次评价与登录手机号或原选单联系信息交给所属门店处理。
- 匿名顾客未登录时，不新增手机号收集入口；其可只提交评价。若选择联系，先完成登录或明确提供联系授权，具体方案属于后续闭环能力。
- 顾客不选择联系，不影响评价提交；评价原文不向技师端公开展示。

### 6.4 提交与结果

- 星级未选择：提交按钮禁用并提示“请选择本次体验评分”。
- 网络提交中：同一按钮进入加载态并防重复点击；失败保留星级、标签和文字，显示可重试原因。
- 成功：显示“感谢您的评价”，说明“已记录到本次到店服务”；返回后即时把该记录置为已评价。
- 已存在评价：后端返回既有结果时前端不再创建第二条；展示“本次服务已评价”，不误报提交失败。

## 7. 状态、权限与数据边界

### 7.1 状态机

```text
未结束 ──服务端确认结束──> 可评价 ──提交成功/幂等命中──> 已评价
   │                            │
   └──不可评价                  └──关闭、断网、失败：仍为可评价
```

- `can_evaluate=true` 且 `evaluated=false` 是唯一待评价判断；前端不得根据页面文案、提交时间或本地缓存推断。
- 没有权威服务结束时间时，提交评价必须被服务端拒绝；前端提示“服务结束确认后即可评价”，不能伪造成功。
- `post_service_present`、`cleaning`、`released` 等运营状态不改变顾客侧“服务已完成”的含义。
- 同一选单重复提交必须幂等；接口返回既有结果，不建立第二条评价。

### 7.2 授权与隐私

- 原选单令牌可评价其所属记录；Bearer 令牌只能评价当前顾客本人记录；越权一律按不存在处理。
- 单设备登录被替换后，旧 Bearer 令牌失效；不得用本地缓存恢复身份或评价资格。
- 不在分析埋点写入评价原文、标签明细、星级与手机号的可逆组合、验证码、JWT 或选单令牌。
- 服务端保存原文时按最小权限访问、审计读取；管理端和技师端的可见范围、导出、留存期和脱敏规则须在闭环能力上线前单独立约。

## 8. 门店闭环：分阶段范围

### V1：顾客评价体验重做

使用已有 `rating/tags/note` 和现有资格、幂等契约，完成星级显式选择、分层标签、300 字限制、入口排序、失败恢复、已评价同步与埋点。V1 不新增人工回访承诺、不改技师端和管理端。

实现状态：顾客端本地已完成，待合并、发布与门店真机验收。

### V1.1：低分反馈闭环（需跨端确认后实施）

仅在顾客主动开启联系授权且满足门店权限时，产生“需跟进”任务。最小契约应含：`feedback_id`、所属门店、触发时间、星级分桶、顾客授权状态、负责人、状态、处理时间和审计事件；不得把完整原文无差别推送给全体技师。

建议状态：`new → acknowledged → contacted → resolved | closed`。负责人、响应时限、对顾客可见的处理结果和异常升级规则由运营负责人确认后才可上线。

### V2：体验洞察

仅展示门店级聚合趋势、标签占比与样本量，设置最小样本阈值，避免把少量评价归因到具体员工。任何将评价用于绩效、提成或自动营销的方案都必须另立 PRD、合法性评估和员工沟通。

## 9. 埋点与指标

### 9.1 事件

| 事件 | 关键属性（均为非敏感、不可逆值） |
|---|---|
| `service_feedback_entry_impression` | entry_type、service_status、member_bucket |
| `service_feedback_entry_click` | entry_type |
| `service_feedback_rating_select` | rating_bucket |
| `service_feedback_tag_select` | rating_bucket、tag_count |
| `service_feedback_submit` | entry_type、rating_bucket、tag_count、note_present |
| `service_feedback_result` | result=success/duplicate/failure、failure_code |
| `service_feedback_close` | entry_type、rating_selected、form_dirty |
| `service_feedback_follow_up_opt_in` | rating_bucket、enabled |

禁止传输评价原文、具体标签、手机号、选单令牌、JWT、服务位名称或可将小样本反推到个人的组合字段。

### 9.2 指标口径

- 主指标：`评价提交成功数 ÷ 评价表单打开数`。
- 体验指标：`表单打开数 ÷ 有资格评价记录的入口曝光数`、星级选择后提交完成率、失败重试成功率。
- 质量指标：星级分布、低分标签分布、顾客主动联系授权率（仅聚合）。
- 护栏：再次选购点击成功率、评价接口幂等率、越权拦截率、服务未结束误入评价率、页面错误率。

先连续采集 14 天基线，再由产品、门店和运营共同设定目标；没有基线不得凭空承诺好评率或回访时效。

## 10. 用户故事与验收

### Story 1：完成服务后快速评价

作为服务已完成的顾客，我希望用很少步骤表达本次体验。

- [ ] 只有 `can_evaluate=true && evaluated=false` 时出现评价入口。
- [ ] 星级初始未选择，未选择无法提交；选中后有文字反馈。
- [ ] 标签可选、最多 3 个；文案随星级切换且无内部字段。
- [ ] 文字选填且限制为 300 字；超出限制有可理解提示。
- [ ] 成功、重复、失败三种结果均有不同且真实的反馈。

### Story 2：不评价也能继续选择

作为刚结束服务的顾客，我可能只想继续选项目。

- [ ] 服务结束页不会自动打开评价弹窗。
- [ ] 关闭评价、跳过评价和再次选购不会把记录标成已评价。
- [ ] 再次选购建立独立会话，不复制旧项目，不影响旧服务、价格快照和评价资格。

### Story 3：回家后完成待评价

作为登录顾客，我希望从“我的”找到未评价记录。

- [ ] 待评价数量只计算有资格且未评价的本人记录；0 条时不显示空卡。
- [ ] 到店记录、详情与完成页看到的资格状态一致。
- [ ] 提交后该记录立即从待评价筛选移除，返回原筛选与滚动位置。
- [ ] 会话被替换、记录不存在或无权限时，不泄漏他人信息。

### Story 4：网络与无障碍

- [ ] 弱网或断网提交失败不清空已填内容，恢复网络后可重试。
- [ ] 触控目标不小于 44px，读屏可读出当前星级和选择状态；焦点进入弹层、关闭后返回触发入口。
- [ ] 尊重“减少动态效果”系统设置；不以动效作为唯一提交状态提示。
- [ ] 360–520px、横竖屏、字体放大下不遮挡底部提交按钮。

## 12. 发布与验收门槛

实施时需同时完成：顾客端交互测试、评价接口资格/越权/幂等测试、生产构建、`git diff --check`；若启用低分联系闭环，还需同步更新跨端契约、权限、审计和管理端/技师端验收。发布后应核验生产首页、健康接口、评价入口静态资源与匿名/登录两条真实但非敏感测试路径。

自动化测试和公网探针只能证明技术可用，不能替代门店现场营业验收。
