## 0. 为什么补这组 PRD

现有 `admin-platform-redesign-v2.md` 定义了角色、订单/服务位/评价状态机、信息架构和验收原则，但它解决的是“平台怎么组织”。

这组 PRD 补齐的是每个业务板块**可被工程实现的业务逻辑**：

- 谁在什么门店范围操作；
- 业务对象有哪些状态，什么动作允许状态转换；
- 哪些规则是硬约束，哪些是配置；
- 异常怎么处理，谁负责，怎么审计；
- 指标如何定义，什么情况下不能给结论；
- 哪些能力当前没有实现，优先级是什么。

每份 PRD 都标注：

- 🔶 **Assumption**：基于现有产品/代码推断，尚未经业务确认；
- 🔵 **Open Question**：必须由业务、财务、法务或门店确认；
- **当前实现差距**：代码与目标的差异，不把“计划”写成“已完成”。

## 1. 产品原则

1. **一个事实一个来源**：订单状态、服务位状态、评价状态只能由后端权威字段决定。
2. **角色叠加**：店长 = 技师 + 门店权限；不为店长复制第二套端。
3. **门店是数据边界**：所有运营数据带 store scope；总部跨店操作必须显式选择门店并审计。
4. **任务优先**：工作台先回答“现在需要处理什么”，不是展示所有数据表。
5. **系统处理常规动作，人只处理异常**：确认、超时、常规流转由系统执行；人工介入必须是异常动作且留理由。
6. **先定义指标，再画图**：没有口径、时间范围、数据来源的指标不上线。
7. **不伪造成熟度**：没有真实支付、库存、排班能力时，不展示对应承诺。

## 3. 角色与授权边界

| 角色 | 数据范围 | 典型职责 | 不能做 |
|---|---|---|---|
| 总部管理员 `brand_admin` | 全品牌 | 门店、标准目录、员工/授权、跨店经营 | 代替门店做日常服务动作 |
| 总部运营 `hq_operator` | 品牌/授权范围 | 内容、营销、审核、跨店查看 | 修改总部管理员/品牌授权 |
| 店长 `store_manager` | 本店 | 现场订单查看、服务位、评价、标签、本店上下架 | 编辑总部主数据、跨店修改 |
| 店员 `store_staff` | 本店只读 | 到店选单、服务位查看 | 看顾客隐私、改目录、退款 |
| 技师 `technician` | 本人服务 | 今日服务、服务记录、顾客标签、评价查看 | 操作订单状态、改门店配置 |

全局硬规则：

- 店长必须有有效 Technician 档案；
- 店长绑定技师后同时通过 manager 和 technician 授权；
- 离职/停用/撤销授权立即失效令牌；
- 历史订单、服务、评价、审计不物理删除；
- 顾客敏感信息按最小必要展示。

## 5. 跨模块状态机总览

### 4.1 门店

```text
draft → preparing → open ⇄ suspended → closed
```

`open` 前必须完成：门店资料、负责人、服务位、至少一个已发布项目、页面、员工/技师账号、顾客入口。

### 4.2 选单 → 服务订单

```text
selection: draft → submitted → confirmed → in_service → completed
                   └→ cancelled / expired
order:      pending_payment → paid → confirmed → in_service → pending_checkout → completed
```

选单是顾客选择与现场排队事实；订单是结算与履约事实。两者必须通过 `fulfillment_order_id` 显式关联，不允许双事实各算一套收入。

### 4.3 服务位

```text
available → held → waiting_service → in_service → post_service_present → cleaning → released
                                                    └→ conflict / exception
```

### 4.4 评价

```text
created → open → in_progress → resolved
                       └→ dismissed
```

原文不可修改；跟进追加历史；低分为待处理，不自动等于投诉成立。

### 4.5 技师

```text
employment: active / leave / resigned
work_state: available / busy / off
account:    not_opened / invited / active / disabled
```

三条轴不可合并为一个 `status`。

## 6. 优先级

排序采用 **RICE 简化版**，因为本阶段数据有限，不能假装精确：

- **Reach**：受影响的门店/员工/顾客范围；
- **Impact**：对交易正确性、门店效率、总部管控的影响；
- **Confidence**：是否有代码/生产证据，还是假设；
- **Effort**：需要后端模型、迁移、前端、测试的量级。

没有数据支撑的 RICE 分数只用于对齐，不作为承诺。当前结论是：先修正确性和可达性，再做效率工具。

| 优先级 | 事项 | 原因 |
|---|---|---|
| P0 | 门店状态阻断业务 | ✅ 已实现状态闸门，仍需开业清单/闭店检查 |
| P0 | 死页面可达性（页面配置/优惠券/SCRM） | ✅ 已恢复总部/品牌管理员入口 |
| P0 | 总部跨店经营视图 | ✅ 已实现第一版品牌总览，仍需区域/趋势/排名 |
| P0 | 选单/订单双事实边界 | ✅ 已实现对账、异常队列、责任人/SLA |
| P0 | 写操作幂等与前后值审计 | 弱网/并发下的数据风险 |
| P1 | 目录 master + 门店覆盖 + 批量发布 | 连锁标准化基础 |
| P1 | 技师档案、排班、请假审批 | ✅ 已实现审批/周排班/看板/复制周 |
| P1 | 顾客标签/分群/评价跟进历史 | 顾客运营基础 |
| P1 | 结算详情、分页、状态全集 | ⏳ 部分：只读+对账已实现，详情/分页仍待做 |
| P1 | 经营分析口径、日期、时区、利用率 | 决策可信度 |
| P1 | 页面配置/优惠券/自动化表单化 | 运营可用性 |
| P2 | 批量操作、审批流、版本回滚、数据质量监控 | 规模化效率 |

## 7. 交付顺序

1. **业务规则冻结**：确认本套 PRD 的开放问题，尤其是商品定位、总部跨店、排班、标签归属、退款权限；
2. **P0 修正确性**：门店状态、死页、双事实、总部视图、幂等审计；
3. **P1 补闭环**：目录、技师、顾客运营、结算、分析、配置类页面；
4. **P2 提效率**：批量、审批、回滚、导入导出；
5. 每项必须有测试、构建、发布和生产验证，不以文档代替上线。

## 8. 完成定义（DoD）

一个模块只有同时满足以下条件才算“产品逻辑补完”：

- [ ] PRD 中的角色、范围、状态机、异常、指标全部有明确规则；
- [ ] 后端有权限、门店范围、状态机、幂等和审计；
- [ ] 前端有加载、空、错、无权限、重试和移动端适配；
- [ ] 关键路径有自动化测试或可复现的生产冒烟；
- [ ] 指标有口径、时间范围、数据来源和更新时间；
- [ ] 已知开放问题有负责人和决策日期；
- [ ] 已部署并且在生产可操作。

## 10. 使用方式

- 工程评审：先读对应模块 PRD 的“业务规则/状态机/验收标准”，再看“当前实现差距”；
- 设计评审：用 PRD 的异常/空态/权限要求检查页面；
- 开发交付：每个需求必须引用 PRD 编号和验收项；
- 变更管理：业务规则变更必须更新 PRD、验收清单和审计说明，不允许只在代码里改。
